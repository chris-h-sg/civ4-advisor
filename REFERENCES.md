## Game's own XML rules data

Static reference data (unit stats, building costs, tech tree, civic effects) lives in the game/mod's `Assets` folder as plain XML. To be parsed once and cached by the harness — not part of the per-turn state payload.

Layout confirmed against the local install (path in `config.local.json`): tunables in `Assets\XML\GlobalDefines.xml`, and one file per concept under `Assets\XML\GameInfo\` (`CIV4ProcessInfo.xml`, etc.). Each entry carries the `<Type>` key the state schema uses, so state joins against these with no mapping table. BTS expansion content lives under `Beyond the Sword\Assets\XML\` and overrides the base tree.

## Research-rate mechanics (verified for schema's `beakersPerTurn`/`turnsLeft` semantics)

Verified 2026-08 directly against the vanilla BTS game-core C++ source — **`https://github.com/dguenms/beyond-the-sword-sdk`** ("Unedited CvGameCoreDLL sources for Civ IV Beyond the Sword"), `CvGameCoreDLL/CvPlayer.cpp` — not against forum folklore. Read only, never vendored (per the no-Firaxis-code rule in CLAUDE.md). Key findings:

- **The "hidden research bonuses" are real, and they scale the *rate*, not the tech cost.** `CvPlayer::calculateResearchModifier(eTech)` returns `100 + TECH_COST_TOTAL_KNOWN_TEAM_MODIFIER × (met alive teams that know eTech) / (alive teams) + TECH_COST_KNOWN_PREREQ_MODIFIER × (eTech's OR-prerequisites the team already knows)`. `calculateBaseNetResearch` then computes `(BASE_RESEARCH_RATE + research-slider commerce) × modifier / 100` — so raw city beakers get multiplied by the modifier, plus a flat free base beaker, before anything is applied to the tech.
- **Constant values** (confirmed in the local install's `Beyond the Sword\Assets\XML\GlobalDefines.xml`, not assumed): `BASE_RESEARCH_RATE = 1`, `TECH_COST_TOTAL_KNOWN_TEAM_MODIFIER = 30`, `TECH_COST_KNOWN_PREREQ_MODIFIER = 20`.
- **`getResearchTurnsLeft` ≈ ceil(remaining team cost / Σ calculateResearchRate), min 1 — but research overflow from the previously finished tech is subtracted from the remaining cost first** (modifier-adjusted, via `getOverflowResearch`), so displayed turns-left can undershoot naive division right after a tech completes. Team-mate rates are summed too (irrelevant single-player).
- **Schema consequence:** `player.beakersPerTurn` = `CyPlayer.calculateResearchRate(-1)` — the modifier-inclusive figure consistent with `turnsLeft` — NOT the raw slider split of commerce, which would silently understate research by the hidden bonuses. All needed methods (`calculateResearchRate`, `calculateResearchModifier`, `calculateGoldRate`, `getResearchTurnsLeft`, `getOverflowResearch`) are confirmed exposed on `CyPlayer` per the BUG API reference (`.../PythonAPI/Classes/CyPlayer.html`).

## Unit/city API semantics (verified while implementing schema increment ②)

Checked 2026-08 against the BUG Python API reference, the base game's own Python in the local install (`Beyond the Sword\Assets\Python`, authoritative for how Firaxis themselves read these values), and the BTS game-core C++ source (`https://github.com/dguenms/beyond-the-sword-sdk`) where the Python layer wasn't conclusive.

- **`CyUnit.movesLeft()` is in internal movement points, not displayed moves; `baseMoves()` is in displayed moves.** `Screens/CvMainInterface.py:2453-2462` divides `movesLeft()` by `gc.getMOVE_DENOMINATOR()`, rounds the quotient *up*, and prints it as `"%d/%d"` against `baseMoves()` — which is what establishes that `baseMoves()` is already in display units. `MOVE_DENOMINATOR = 60` per the install's `Assets\XML\GlobalDefines.xml:181`. `maxMoves()` is `baseMoves()` in internal units. `baseMoves()` is `unitInfo.getMoves() + getExtraMoves() + team extra moves for the domain`, so it reflects promotions, not just the XML base.
- **`movesLeft()` is unusable at our export timing, verified live.** The per-turn reset is `setMoves(0)` inside `CvUnit::doTurn()`, which runs when the player's next turn activates — after `onEndGameTurn` has fired and the state file is already written. A turn-2 capture confirmed it: a warrior that had moved exported `0`. The schema therefore exports `moves` (`baseMoves()`) instead; see CLAUDE.md.
- **`CyCity.getProductionNeeded()` returns `MAX_INT` when nothing can complete.** Verified in `CvGameCoreDLL/CvCity.cpp`: the switch on the head order node breaks (rather than returns) for `ORDER_MAINTAIN`, and a NULL head node skips the switch entirely — both fall through to `return MAX_INT`. So an empty queue *and* an active process both yield 2147483647.
- **`CvCity::getProductionDifference`** (what `getCurrentProductionDifference(bIgnoreFood, bOverflow)` delegates to) returns 0 during disorder, and with `bOverflow` adds `getOverflowProduction() + getFeatureProduction()` — one-off amounts, not a recurring rate. The city screen passes `bOverflow=True` anyway, so matching the UI means inheriting that.
- **The food/hammer halves of production subtract cleanly, and the engine itself does that subtraction** (verified 2026-08 in `CvCity.cpp` for schema increment ⑥). `getProductionDifference` (`:3097-3110`) is `if (isDisorder()) return 0;` then `iFoodProduction = bFoodProduction ? std::max(0, getYieldRate(YIELD_FOOD) - foodConsumption(true)) : 0;` and finally `((getBaseYieldRate(YIELD_PRODUCTION) + iOverflow) * getBaseYieldRateModifier(...)) / 100 + iFoodProduction`. **`bFoodProduction` gates exactly one additive term and touches nothing else** — the hammer expression is identical between the two calls — so `(False, True) - (True, True)` is exact in every state, not an approximation. Under disorder both sides return 0 and the difference is a degenerate-but-correct 0. This is stronger than "probably subtracts", which is what the increment set out to check.
  - **`CvCity::getProductionBarPercentages` (`:12410-12428`) computes precisely this**, to size the city screen's two-tone production bar: `iProductionDiffNoFood = getCurrentProductionDifference(true, true); iProductionDiffJustFood = getCurrentProductionDifference(false, true) - iProductionDiffNoFood;`. So the exported split is the engine's own decomposition read the way the game reads it, not one the mod invents. Both overloads are confirmed exposed to Python (`CyCityInterface1.cpp:83`).
  - **Only a unit order can be food-fed, and `bFood` is not the whole test.** `CvCity::isFoodProduction()` (`:2581-2605`) returns false for `ORDER_CONSTRUCT`/`ORDER_CREATE`/`ORDER_MAINTAIN` — buildings, projects and processes never consume food, so the food half is 0 for all of them. But the unit overload (`:2608`) is `GC.getUnitInfo(eUnit).isFoodProduction()` **OR** (`GET_PLAYER(...).isMilitaryFoodProduction()` AND the unit `isMilitaryProduction()`) — i.e. a civic with `isMilitaryFoodProduction` (Police State) makes every military unit food-fed. **Consequence: the qualifying set is wider than `<bFood>` in `CIV4UnitInfos.xml`**, so a harness inferring food-fed-ness from that flag alone is incomplete, and the exported field is authoritative where the XML is not. Out of reach before turn 50, but it is the reason the split is exported rather than reconstructed.
  - **`foodDifference` corroborates the zero.** `CvCity::foodDifference` (`:4508-4535`) returns 0 under disorder and, when `isFoodProduction()`, clamps to `std::min(0, ...)` — which is why `foodPerTurn` reads 0 rather than negative exactly while a food build is queued, the observation the harness's old inference keyed on.
- **Production order kind is read via the `isProductionUnit`/`Building`/`Project`/`Process` cascade**, each paired with its `getProductionX()` id and the matching `gc.getXInfo(...).getType()`. Pattern taken verbatim from `pyWB/CvWBDesc.py:782-789`, which serializes a city for WorldBuilder.
- **Happiness/health/culture accessor arguments**, as used by `Screens/CvMainInterface.py` and `PyHelpers.py`: `happyLevel()`, `unhappyLevel(0)`, `goodHealth()`, `badHealth(False)`, `foodDifference(True)`, and `getCulture(pCity.getOwner())` — the last paired with `getCultureThreshold()` for the culture bar, confirming it's the owner's share (`getCulture` is per-player within a city) that drives border expansion.
- **Unit/city iteration** uses the `(object, cursor)` pair returned by `firstUnit(bRev)`/`nextUnit(cursor, bRev)` and `firstCity`/`nextCity`, looping while the object is truthy — `PyHelpers.py:256-260` and `:314-320`, which also supply the validity filters (`isDead()` for units, `isNone()` plus an owner check for cities).

## Plot/map API semantics (verified while implementing schema increment ③)

Checked 2026-08 against the BUG Python API reference, the base game's own Python in the local install, and the BTS game-core C++ source (`https://github.com/dguenms/beyond-the-sword-sdk`). The Python layer was **not** conclusive here — the base game's own Python never calls `getRevealed*` or `calculateYield` at all — so most of this came from the SDK.

- **The engine remembers exactly three things per team, and nothing else.** `CvPlot` holds `m_aiRevealedOwner`, `m_aeRevealedImprovementType` and `m_aeRevealedRouteType`. There is no revealed variant of terrain, plot type, feature, bonus or river anywhere in `CvPlot` or in the `CyPlot` Python surface — the engine has no memory of them to return. Its own tile mouseover (`CvGameTextMgr::setPlotHelp`) reads `getTerrainType()`, `getFeatureType()`, `isHills()`, `isPeak()` live and the resource via `getBonusType(getActiveTeam())`. So exporting live values for those is not an approximation of the player's view; it is the same call the game makes to draw its own tooltip. Consequence to keep in mind: a forest chopped under fog updates immediately — the game's own leak, in its own UI.
- **`getBonusType(eTeam)` is team-aware but not fog-aware.** Its only gate is `!isHasTech(GC.getBonusInfo(...).getTechReveal()) && !isForceRevealedBonus(...)`. Correct behaviour: a resource stays visible through fog once revealed, but one you lack the tech for stays hidden.
- **`bDebug=True` on any revealed getter bypasses to live truth whenever `isDebugMode()` is on** (`getRevealedImprovementType`, `getRevealedOwner`, `getRevealedRouteType`, `isRevealed`, `isVisible` all start with the same `if (bDebug && GC.getGameINLINE().isDebugMode())`). Always pass `False`: the failure would be silent and total (full-map truth) if WorldBuilder or the Chipotle cheat were toggled.
- **`calculateYield(eYield, bDisplay=True)` is the displayed yield**, used by both display paths: `CvPlot::updateSymbols()` (the yield icons on the map) and `CvGameTextMgr::setPlotHelp` (the mouseover). `bDisplay=true` also swaps in `getRevealedOwner`/`getRevealedImprovementType`/`getRevealedRouteType` internally, so it is the fog-honest choice too. `getYield()` is the cached `bDisplay=false` variant (live improvement/route/owner) — don't use it. Three inherited quirks:
  - **It reads `GC.getGameINLINE().getActiveTeam()` / `getActivePlayer()`, not any team you can pass.** There is no API for another player's displayed yield. Safe in single player — `CvGame::setActivePlayer` is called only from `CvGame::read`, gated on `!isGameMultiPlayer()`, selecting the first human, and never rotates while the AI civs take their turns — but the mod asserts on it rather than relying on it silently.
  - **`if (!isPotentialCityWork()) return 0;`** — a plot with no land anywhere in its 21-tile city cross returns all-zero yields regardless of terrain, so deep ocean reads `[0,0,0]`. Matches the map (no yield icons out there). Same for `getTerrainType() == NO_TERRAIN`.
  - **On an unowned tile it substitutes `getActivePlayer()` as the owner**, so player-specific effects (Financial's `getExtraYieldThreshold`, golden-age yields) apply to land nobody owns. Again, what the map shows.
- **Plot type is one enum, not flags.** `m_ePlotType` is stored independently of `m_eTerrainType` — a peak still has terrain underneath. `isPeak()`/`isHills()`/`isFlatlands()`/`isWater()` are literally `getPlotType() == PLOT_PEAK / PLOT_HILLS / PLOT_LAND / PLOT_OCEAN` (`CvEnums.h:647`, marked "Exposed to Python"). Two traps: the individual `PlotTypes.PLOT_*` constants are never referenced in the base game's Python (only `NO_PLOT` and `NUM_PLOT_TYPES` are), so the mod reads the predicates instead; and `PlotTypes` has **no XML info object**, so there is no `getPlotTypeInfo(i).getType()` — the game's own serializer `CvWBDesc.py` writes it as a raw integer (`PlotType=%d`).
- **`TERRAIN_PEAK` and `TERRAIN_HILL` in `CIV4TerrainInfos.xml` are vestigial and misleading** — both are flagged `<bWater>1</bWater>`. `CvPlot::setPlotType` normalizes terrain to `LAND_TERRAIN`/`SHALLOW_WATER_TERRAIN`/`DEEP_WATER_TERRAIN`, which `GlobalDefines.xml` defines as `TERRAIN_GRASS`/`TERRAIN_COAST`/`TERRAIN_OCEAN`. Nothing resolves to either. Don't derive "is water" from a terrain-XML join.
- **`isRiver()` is `getRiverCrossingCount() > 0`** — the tile has a river along one of its own edges. The canonical storage is two booleans plus flow directions per plot (`CvWBDesc.py` writes exactly `isNOfRiver` / `RiverNSDirection` / `isWOfRiver` / `RiverWEDirection`), and **the flags are named for where the river is, not the edge**: from `CvPlot::updateRiverCrossing`, the `DIRECTION_SOUTH` case is `bValid = isNOfRiver()`, so "plot P is North Of River" means the river runs along **P's south edge**; `isWOfRiver()` likewise means the river is on P's **east** edge. Anyone implementing edge geometry from the method names alone would invert it silently. River crossings only exist between two non-water plots.
- **`isFreshWater()` is land-only** and is river OR adjacent-to-a-lake OR adjacent to a feature with `isAddsFreshWater` (flood plains, oasis) — so it is not derivable from any single tile's own fields. **`isLake()` is an area property** (`area()->isLake()`), and lakes share `TERRAIN_COAST` with coastal sea, so nothing else in a tile distinguishes them.
- **Worked tiles must be read city-side.** `CvPlot::isBeingWorked()` is `getWorkingCity() && workingCity->isWorkingPlot(this)` — live truth with no visibility check. The engine *has* a fog-aware wrapper, `CvPlot::isVisibleWorked()` (gates on plot team == active team), but it is one of the few `CvPlot` methods **not** marked "Exposed to Python" in `CvPlot.h`. Reading `CyCity.isWorkingPlotByIndex(i)` / `getCityIndexPlot(i)` over our own cities is honest by construction and ~10x cheaper. `gc.getNUM_CITY_PLOTS()` is 21 (`CITY_PLOTS_RADIUS` 2 → 5x5 minus corners); `gc.getCITY_HOME_PLOT()` is the centre index.
- **The blue-circle city-site indicator — considered and deliberately not exported.** Two distinct things: `getFoundValue(player)`, the raw number, is **cheat-gated** — both places `setPlotHelp` prints it sit inside `if (bCtrl && gDLL->getChtLvl() > 0)` / `if (bShift && !bAlt && gDLL->getChtLvl() > 0)` blocks with unlocalized debug text — so exporting it would hand over more than the player sees. `isBestAdjacentFound(player)` is the fog-honest boolean (local maximum of found value among *revealed* neighbours) and matches blue-circle behaviour, though not provably so: the renderer is in the EXE, not the open-sourced DLL. It was dropped on **cost**: it calls `AI_foundValue` fresh and uncached for the plot plus up to 8 neighbours — nine full 21-tile fat-cross evaluations per tile, ~3,600 per export at 400 revealed tiles, plausibly more than the entire rest of the map section. And the obvious cheap prefilter is unsound: `getFoundValue` caches `AI_foundValue(x, y, -1, bStartingLoc=**true**)` while `isBestAdjacentFound` uses `bStartingLoc=**false**` (`CvPlayerAI.h:71`), so they are different valuations. Found values *are* maintained for human players (`AI_doTurnUnitsPre` → `AI_updateFoundValues`, itself gated on `isRevealed`), so this is a cost decision, not an availability one.
- **`CvMap` plot indexing is row-major**: `plotX(i)` is `i % getGridWidth()`, `plotY(i)` is `i / getGridWidth()`. So iterating `for y: for x: plot(x, y)` matches `plotByIndex` order while getting the coordinates for free instead of via two extra calls.
- **Map-section size, measured over candidate formats** on a synthesized but realistic turn-20 reveal (399 tiles, 84x52 map, ~6% currently visible): per-tile objects pretty-printed **139 KB**; one line per tile, all fields **92 KB**; **one line per tile with defaults omitted 29 KB** (38 KB once `plotType`/`lake`/`freshWater` were added); column-oriented parallel arrays **38 KB**; `columns` header + array-of-arrays **39 KB**; an ASCII grid of terrain/hills/feature/river/bonus glyphs **1.1 KB**. Two things decided it: pruning beats every restructuring because it removes the ~60% of cells a rectangular layout still has to fill, and the grid — though 27x smaller and the best *prompt* form — is lossy and derivable from the objects, so it belongs in the harness. Line lengths of pruned tiles: median 96, p90 120, max 165, with ~73% over the serializer's 88-char inline threshold, which is what forced the always-inline `_Record`.
- **Map-scan cost, measured in-game 2026-08-02** (84x52 map, 4368 plots, `LOG_TIMINGS = True`): **4 ms** for the whole map section at 52 revealed tiles and again at 59; 10 ms on the very first export of a session, which is warm-up. Tile count barely moving the figure says the cost is dominated by the fixed full-grid `isRevealed` sweep rather than per-tile extraction, so the marginal cost of a larger reveal is small. Comfortably under the 250 ms warning threshold.

## Diplomacy and foreign-entity API semantics (verified while implementing schema increment ④)

Checked 2026-08 against the BTS game-core C++ source (`https://github.com/dguenms/beyond-the-sword-sdk`, `develop` branch), the base game's own Python in the local install, and the install's XML. Unlike increment ③, the Python layer *was* conclusive here — the advisor screens do most of this already. Line numbers are from that SDK checkout.

- **You have "met" the barbarians, and are at war with them, from turn 0.** `CvGame::initDiplomacy` has every barbarian and minor team `declareWar` on every civ team at game start (`CvGame.cpp:614-621`), and `CvTeam::declareWar` calls `meet(eTeam, false)` (`CvTeam.cpp:1136`), which is mutual (`CvTeam::meet` → `makeHasMet` on both sides). So `isHasMet(BARBARIAN_TEAM)` and `isAtWar(BARBARIAN_TEAM)` both report true immediately. **A `contacts` loop written on `isHasMet` alone emits a barbarian contact, at war, with a meaningless attitude, in every export from turn 1.** The base game filters for exactly this: every rival loop in `Screens/CvForeignAdvisor.py` (`:269`, `:290`, `:313`, `:436`, `:545`) and `Screens/CvExoticForeignAdvisor.py` (`:311`, `:403`) reads `isAlive() and not isBarbarian() and not isMinorCiv() and isHasMet(...)`.
- **Attitude is a five-value bucket and the numeric score is not reachable from Python.** `AI_getAttitude` returns `AttitudeTypes` (`CvEnums.h:1947-1958`, "Exposed to Python") via `AI_getAttitudeFromValue`, which buckets the hidden integer at ±3 / ±10 (`CvPlayerAI.cpp:4713-4743`). `AI_getAttitudeVal` is **absent from `CyPlayerInterface1/2.cpp`**, so the bucket is the most that could leak even by accident. `ATTITUDE_FURIOUS…FRIENDLY` are real XML `Type` keys (`Assets\XML\BasicInfos\CIV4AttitudeInfos.xml`) reached through `gc.getAttitudeInfo(i)` (`CyGlobalContextInterface3.cpp:20`), so it joins like every other enum. The exact call is in the base game's own Python: `CvForeignAdvisor.py:531-532`.
- **Attitude display is gated on `isHasMet` and nothing else — no espionage tier.** The leaderhead tooltip prints it inside `if (…isHasMet(…))` (`CvDLLWidgetData.cpp:3185` → `:3201`), as does `parseLeaderHeadHelp` (`CvGameTextMgr.cpp:11397` → `:11401`). Note the tooltip shows attitude only for non-human rivals (`CvDLLWidgetData.cpp:3192`) — irrelevant in single player, relevant if this file is ever produced in MP.
- **Foreign units: `plot.isVisible(team, False) and not unit.isInvisible(team, False)`**, iterating each player's own unit list rather than sweeping plots. Straight from `Screens/CvMilitaryAdvisor.py:288-290`, which loops `PyPlayer(i)` over `range(gc.getMAX_PLAYERS())` (`:281-284`) — **including the barbarian player**, who sits at the last index (`CvDefines.h:33-36`: `MAX_PLAYERS == MAX_CIV_PLAYERS + 1`, `BARBARIAN_PLAYER == (PlayerTypes)MAX_CIV_PLAYERS`). Bounded by unit count rather than the 4368 plots.
- **Invisibility is nearly a no-op in turns 1–20, but honour it anyway for cargo.** `CvUnit::isInvisible` returns true only for `alwaysInvisible()`, `isCargo()`, or an undetected `InvisibleType`. `alwaysInvisible()` is `m_pUnitInfo->isInvisible()`, and scanning the install's `CIV4UnitInfos.xml` exactly **two of 123 units** set `<bInvisible>1</bInvisible>`: `UNIT_SPY` and `UNIT_GREAT_SPY`. Neither exists that early. The live branch is cargo — `bCheckCargo` defaults to `true` (`CvUnit.h:376`) and the Python binding is 2-arg (`CyUnitInterface1.cpp:218`) — so a unit loaded on a Galley (earliest `<iCargo>` carrier) reports invisible, which is what the map shows too.
- **`getVisualOwner()` masks hidden-nationality units as barbarian** unless they're in one of their owner's cities (`CvUnit::getVisualOwner`). No such unit exists before Astronomy, but it's the honest getter. **It takes no team argument in Python** (`CyUnitInterface1.cpp:345`) and falls back to `getActiveTeam()` — the same active-team dependency as `calculateYield(bDisplay=True)`, which is why the assertion was hoisted out of `_buildMap` into `buildState`.
- **`CyCity.isRevealed(team, bDebug)` is a per-city flag and is STRICTER than the tile being revealed.** It reads `m_abRevealed[eIndex]` (`CvCity.cpp:8790`-ish). `CvCity::init` reveals a new city only to teams for which the plot is currently **visible** (`CvCity.cpp:229-237` — `isVisible`, not `isRevealed`), and `CvPlot::setRevealed` propagates it both ways (`CvPlot.cpp:7144-7147`, `:7182-7186`) from a block that sits *outside* the `if (isRevealed != bNewValue)` change guard, so it re-runs on every visibility refresh. **Consequence: a city founded on a tile you revealed long ago but cannot currently see is not revealed to you.** This is what kills the plot-sweep implementation — `plot.getPlotCity()` is live truth and would surface exactly those.
- **A revealed city's name, size and capital star are live and ungated, and that matches the UI.** The billboard entity's visibility is `CvDLLEntity::setVisible(isRevealed(activeTeam, true))` (`CvCity.cpp:1115`) — *revealed*, so nameplates persist under fog — and the strings are unconditional live reads: `buildCityBillboardCityNameString` is `getName()` (`CvGameTextMgr.cpp:12212`), `buildCityBillboardCitySizeString` is `getPopulation()` (`:12259`). The engine clearly knows how to gate: the defence modifier is wrapped in `if (pCity->isVisible(activeTeam, true))` (`:12199`) and the happy/health icons in `if (pCity->canBeSelected())` (`:12108`), while `getFoodBarPercentages`/`getProductionBarPercentages` bail outright on `!canBeSelected()` (`CvCity.cpp:12380`, `:12399`; `canBeSelected` is own-team / debug / investigated plot / active passive espionage mission, `:12410`). So foreign city internals genuinely are not shown, and the ungated fields genuinely are.
- **`CvCity::isStarCity()` is literally `return isCapital();`** (`CvCity.cpp:12439-12442`) — `DllExport`, declared under "Billboard appearance controls" (`CvCity.h:832`), with **zero callers anywhere in the DLL**, i.e. a hook that exists solely for the EXE renderer, gated on neither team nor visibility. The corroboration is `buildCityBillboardIconString` drawing its silver star for `isGovernmentCenter() && !(isCapital())` (`CvGameTextMgr.cpp:12102`) — the `!isCapital()` avoids double-starring a capital that already has one. `isCapital()` is exposed (`CyCityInterface1.cpp:113`). *This one was initially reported the wrong way round from reading only the icon-string builder; the dedicated hook is the answer.*
- **Foreign unit damage is player-visible.** `CvGameTextMgr::setPlotListHelp` (`:1198`) folds `getDamage()` / `currHitPoints()` of every unit on a plot into the stack strength it prints, gated only on `pPlot->isVisible(activeTeam, …)` with no owner check.
- **`isHasMet` is symmetric**, since `CvTeam::meet` calls `makeHasMet` on both sides — so the relation can be asked of our own `CyTeam`, and a rival `CyTeam` (the object exposing their techs and research progress) need never be fetched at all.
- **`plot.isRevealedBarbarian()` looks useful and is not:** it hardcodes `getRevealedOwner(GC.getGame().getActiveTeam(), **true**)` (`CvPlot::isRevealedBarbarian`), i.e. debug-bypassing.
- **Confirmed in live play (2026-08-02, turns 0–27, England vs. China, Emperor, 84x52 Fractal).** Every claim above that was source-only when written has now been watched in game, and the exported file was validated against the whole schema at each step:
  - **Turn 0 exports `contacts: []`** with barbarians pre-met and pre-at-war behind it — the filter is doing the work it was written for.
  - **`isRevealed` really is stricter than the tile being revealed.** With three of China's border tiles revealed but not the city tile, `foreignCities` stayed `[]`; Beijing appeared only once actually seen. This is the claim that killed the plot-sweep implementation, and it holds.
  - **Beijing exported `capital: true`** — the `isStarCity` finding, confirmed at the UI.
  - **Units are visibility-gated, cities are reveal-gated.** A barbarian `UNIT_PANTHER` exported at `(67,23)` with `damage: 92`, `owner: 18`; after moving away it vanished from `foreignUnits` entirely while its tile stayed in `map.tiles` minus `visibleNow`. Beijing, by contrast, persisted under fog.
  - **Met-but-unseen is a real and common state:** `contacts` carried China several turns before any Chinese unit was visible, because `isHasMet` is symmetric while `isVisible` is not.
  - **Attitude matched the in-game tooltip** (`ATTITUDE_CAUTIOUS`), and a four-unit Chinese stack matched the map exactly (two archers on the city tile, one archer plus a worker one tile west).
  - **Cost: the three sections measure 0 ms**, fully populated, against 5–6 ms for the map section at 205 revealed tiles. The Phase 1 estimate that they'd be dominated by the map sweep was right by a wide margin.
- **Still not verified:** `getPopulation()` was seen to persist and read correctly on a fogged city, but was never watched *changing* while fogged, so "the nameplate number stays live under fog" remains inference from the DLL building the string (the renderer is in the EXE, the same limitation that stopped the blue circle in ③). And `CvPlayer::acquireCity` destroying and recreating the city object on capture (`CvPlayer.cpp:1687`) was not traced end to end, so what happens to a city captured while you are not looking is unestablished — out of scope for turns 0–50.

## Connected resources and wonder availability (verified while adding `bonuses`, `coastal`, `wonders`)

Checked 2026-08 against the BUG Python API reference (authoritative for what is actually *exposed* to Python — the deciding factor here), the base game's own Python in the local install, and the install's XML.

- **`CyCity.hasBonus(iBonus)` is the engine's own "is this resource connected to this city" test**, used throughout `CvAdvisorUtils.py` (lines 278, 297, 316, 335, 356) to decide which "resource connected" popup to show. It is boolean and already folds in tech-revealed, correctly-improved, route/river/coast-linked to *this* city, not severed by war, not traded away. Consequence worth knowing: it cannot say *why* a resource is missing — distinguishing "no copper" from "copper in the fat cross, unroaded" needs `map.tiles` joined against it.
- **Quantity is player-level only.** `CyPlayer.getNumAvailableBonuses(eBonus)` (confirmed exposed, and used in `Screens/CvDebugInfoScreen.py:323`) returns the empire-wide count. There is no per-city count and the engine does not model one — a city has the connection or does not. Hence `counts` on `player.bonuses` and membership-only on `cities[].bonuses`.
- **There is no "strategic" flag anywhere, and the obvious reverse lookup does not exist.** `BonusClassType` in `CIV4BonusInfos.xml` looks like the answer and is not — it is a *map-generation clustering* hint (`BONUSCLASS_GENERAL` covers 21 of the 35 bonuses, alongside `GRAIN`/`LIVESTOCK`/`RUSH`/`MODERN`/`WONDER`). More importantly **`CvBonusInfo` exposes no reverse index**: there is no `getNumUnitsWithBonus`/`getNumBuildingsWithBonus` in the Python layer (checked against the BUG reference's full method list for the class — `getHealth`/`getHappiness` are there, those two are not). So a bonus cannot be asked what it unlocks; the relation exists only in the other direction and must be swept.
- **The sweep uses two prerequisite forms, which mean different things.** `CvUnitInfo`/`CvBuildingInfo` both expose `getPrereqAndBonus()` (a single required bonus) and `getPrereqOrBonuses(i)` (fixed-length array of alternatives, any one sufficient — the Spearman's Bronze/Iron/Horse). Array length comes from `gc.getDefineINT('NUM_UNIT_PREREQ_OR_BONUSES')` / `'NUM_BUILDING_PREREQ_OR_BONUSES'`, both `4` in stock BTS (`GlobalDefines.xml:273`, `:277`) — read via the define rather than hardcoded. Unused slots hold `NO_BONUS`. Max entries actually used in stock unit XML: 4.
- **`iHealth`/`iHappiness` are per-bonus XML fields** and are what the city bars credit (`CvAdvisorUtils.py:334`/`355` test `getHappiness() > 0` / `getHealth() > 0` for the popups). Tested strictly positive, not non-zero: negative values are permitted by the engine and would otherwise read as a benefit.
- **`CyCity.isCoastal(iMinWaterSize)` takes an argument and it matters.** Signature confirmed as `BOOL isCoastal(INT iMinWaterSize)`; passed `gc.getMIN_WATER_SIZE_FOR_OCEAN()` (also confirmed exposed). This is *not* "is a neighbouring tile water" — it is adjacency to a water body of at least that size, so a city on a small pond is not coastal and cannot build a Harbour. That is precisely what a hand-rolled adjacency check in the harness would get wrong, which is the argument for exporting it.
- **World-wonder availability is public knowledge, checked rather than assumed.** The game's own Info screen (`Screens/CvInfoScreen.py:1865-1869`) sweeps every player's cities for `hasBuilding` on world-wonder classes and gates **only the builder's identity** on `isHasMet` — an unmet builder's civ and city render as `TXT_KEY_UNKNOWN` while the wonder itself is listed unconditionally. Every player also gets a global popup on completion (`CvEventManager.py:422`). So "the Pyramids are taken" is public; "Hammurabi built them in Babylon" is not. The export carries the former only — no owner, no city, no date.
- **`CyGame.getBuildingClassCreatedCount(eIndex)` is the cheap correct route** (confirmed exposed) rather than the Info screen's city sweep: a sweep needs rivals' city lists and would miss wonders in cities never seen. `CyPlayer.getBuildingClassCount(iIndex)` gives our own national-wonder count.
- **Wonder-ness lives on the building *class*, not the building** — `CvBuildingClassInfo.getMaxGlobalInstances()` (`1` → world wonder, 33 classes in stock BTS) and `getMaxPlayerInstances()` (`1` → national wonder, 13 classes); `-1` is unlimited. `getMaxTeamInstances()` is `-1` for every stock class. Classes are also what a civ's unique replacement shares, so class keys are what the export uses. **`BUILDINGCLASS_PALACE` legitimately carries `iMaxPlayerInstances 1`** and so appears in `national` from turn 0 for every player — correct, not a glitch.
- **`CyCity.hasBuilding()` DOES NOT EXIST, and "the base game calls it" was not sufficient evidence.** This cost a live export: the mod raised `AttributeError: 'CyCity' object has no attribute 'hasBuilding'`, `_exportState` logged it, and no file was written. The base game's own Python calls `pCity.hasBuilding()` in eight places (`PyHelpers.py:470`/`:593`, `CvInfoScreen.py:1356`/`:1865`/`:1884`, `CvMainInterface.py:1964`, `CvWorldBuilderScreen.py:453`/`:1188`), which looks conclusive — but those call sites hold WorldBuilder screen objects and `getPlotCity()` results, not a `CyCity` reached the way the mod reaches one. The real binding is `isHasBuilding`, which the BUG reference itself flags as a compatibility shim that "no longer exists in C++" and forwards to `getNumBuilding`. **Use `getNumBuilding(iBuilding) > 0`** — the underlying method, one fewer layer. Not `getNumRealBuilding`, which excludes FREE buildings and would omit the capital's Palace, the single most expected entry in the field. General lesson: base-game Python proves a method exists *on some object*, not on the object at hand; the BUG per-class reference is the authority for which class exposes what.
- **`BUILDING_` and `BUILDINGCLASS_` keys are not interconvertible by name.** `CvBuildingInfo.getBuildingClassType()` maps one to the other if needed, but string surgery will not: 28 stock buildings have a class whose name differs from their own, and the relation is many-to-one in places (`BUILDING_COAL_PLANT`, `BUILDING_HYDRO_PLANT`, `BUILDING_NUCLEAR_PLANT` → `BUILDINGCLASS_FACTORY`; `BUILDING_UNIVERSITY` → `BUILDINGCLASS_LIBRARY`; `BUILDING_GREAT_PALACE` → `BUILDINGCLASS_COURTHOUSE`). Counted directly from the install's `CIV4BuildingInfos.xml`.
- **Not exposed / rejected:** `isWorldWonderClass`/`isNationalWonderClass`/`isTeamWonderClass`/`isLimitedWonderClass` are used freely in the base game's Python but are **not defined in it** — they come from `CvPythonExtensions` (the C++ binding module), so they'd likely work, but reading the two `getMax*Instances` values directly is equivalent, self-documenting, and avoids depending on a helper whose exact semantics aren't in the API reference.

## Game setup vs. generated-map statistics (the fog-of-war line in the `game` section)

- **Safe — the setup the player chose, all visible on the game-setup screen, all XML-backed with `Type` keys:** `CyMap.getWorldSize()` → `CIV4WorldInfo.xml`, `getClimate()` → `CIV4ClimateInfo.xml`, `getSeaLevel()` → `CIV4SeaLevelInfo.xml`, `CyGame.getHandicapType()` → `CIV4HandicapInfo.xml`, `isOption(i)` over `getNumGameOptionInfos()` → `CIV4GameOptionInfos.xml`, `isVictoryValid(i)` over `getNumVictoryInfos()`. `CyMap.getMapScriptName()` is a plain script filename with no XML behind it. The corresponding `gc.getWorldInfo/getClimateInfo/getSeaLevelInfo/getHandicapInfo/getGameOptionInfo/getVictoryInfo` all exist per the BUG reference.
- **Why these are worth exporting rather than just decorative**, confirmed in the local install's XML: `CLIMATE_ROCKY` carries `iPeakPercent 35` and `iHillRange 7` against `25`/`5` for `CLIMATE_TEMPERATE`; `CLIMATE_ARID` carries `iDesertPercentChange 20`; `SEALEVEL_LOW`/`HIGH` carry `iSeaLevelChange -8`/`+6`. That is exactly "how hilly / how much water should I expect", available before exploring.
- **Not safe — statistics of the map as generated, sitting right next to the safe getters on the same objects:** `CyMap.getLandPlots()` (exact land-tile count of the entire map including everything unrevealed — the *answer* to how much water there is, as opposed to the parameter), `getNumBonuses(eBonus)` / `getNumBonusesOnLand(eBonus)` (how much of a resource exists anywhere), `getNumAreas()` / `getNumLandAreas()` (how many continents exist), `getOwnedPlots()`. Also `CyGame.countCivPlayersAlive()`, which shrinks when a civ is destroyed and would reveal that before the player could learn it.
- **`countCivPlayersEverAlive()` is the safe player count.** Verified in `CvGame.cpp`: it loops `MAX_CIV_PLAYERS` (so barbarians, who sit at that index, are excluded) counting `isEverAlive()` players whose `getParent() == NO_PLAYER` (so colonial vassals are excluded). Being "ever alive" it is constant for the game and cannot leak a death.

## Python hot-reload inside the embedded interpreter (measured, not documented anywhere found)

Established in-game 2026-08-01 by controlled test, because nothing in the community docs surveyed covers it and the failure mode is silent.

- **`reload(module)` returns successfully and does not update the module's code.** No exception, no log line, no partial effect — the next call runs the pre-edit function bodies. This makes it indistinguishable from the mod not being loaded, and it means any apparent hot-reload success is worth suspecting as a game restart in disguise (that is exactly what ours turned out to be).
- **The interpreter is stock CPython 2.4** (`python24.dll` ships at the install root and under `Beyond the Sword\`), so `reload()` is the standard implementation and not a Firaxis reimplementation. The base install ships `.pyc` only for the bundled stdlib under `Assets\Python\System`; game modules have none, and there's no user-side Python cache directory, so stale bytecode isn't the explanation either. Remaining suspect: the engine's own import hook serving cached module source — consistent with the `__file__` behaviour below, though not directly proven.
- **`execfile(path, module.__dict__)` does work**, and is what the mod uses now. Re-executing the source into the *existing* module's namespace keeps the module object's identity, so references held elsewhere (`import AdvisorStateWriter` in the event manager) stay valid and simply see rebound functions. Verified in both directions in a single game session: an edit applied on the next export, and reverting it applied on the export after.
- **Neither `__file__` nor `sys.path` can locate a mod's own source at runtime.** `__file__` is relative to the engine's `Assets/Python` search root regardless of which physical folder supplied the file (even through a deployment junction). `sys.path` is no better — every entry failed `os.path.isfile` for a module known to exist. An absolute path from a config module is the only route found.
- **Reloading is per-module and does not rescue the event manager.** `CvCustomEventManager.py` still needs a full game restart no matter the mechanism: the engine holds an already-instantiated object built from the old class, and re-executing the source can't re-class it. Likewise a module imported *by* the re-executed module (our `LocalConfig`) comes back from the import cache and needs a restart.

## State-extraction prior art (surveyed before designing the state schema)

Searched (2026-08) for anything in the Civ4 community or academia that already dumps structured game state for external consumption. Verdict: **nothing found that exports live Civ4 game state as structured data** — every adjacent project either targets a different game, parses save files offline, or writes human-readable logs. The schema is ours to design, but CivRealm's observation decomposition is worth borrowing (see below). Verification level noted per item; all claims below checked against the project's own README/docs, not just search summaries.

- **civ4save** (`https://github.com/danofsteel32/civ4save`, PyPI `civ4save`, last release 0.7.0, Nov 2022): Python 3 library that parses `.CivBeyondSwordSave` files (zlib-compressed binary "memory dump") and can emit JSON — the closest thing to a Civ4-state-to-JSON tool that exists. Offline save parsing, not live export, and per its own README incomplete: vanilla BTS only (no mods), plot parsing "buggy/inconsistent" past ~136KB saves, CvPlayer/CvTeam parsing not implemented, CvArea "under construction". *Verified against README + PyPI metadata.* Two takeaways: (1) the fragility of binary save parsing is indirect validation of our live-Python-export approach — we read state through the game's own API instead of reverse-engineering the save format; (2) its `xml` CLI command (transforms game XML into Python enums / JSON mappings) is prior art for our planned parse-XML-once-and-cache harness step.
- **pyconsole** (`https://github.com/civ4-mp/pyconsole`): mod + client that opens a local TCP socket (default port 3333) into Civ4's embedded Python via a `CvEventManager` hook, letting an external client run arbitrary Python in the live game. *Verified against README.* No serialization/schema — it avoids the problem by sharing the runtime. Proves live external programmatic access to a running Civ4 game is viable; doesn't change our file-based-IPC decision (sockets add a listener + threading surface inside the game process, exactly the fragility we're avoiding), but worth knowing it exists if file IPC ever becomes limiting.
- **BUG Autolog** (option surface verified via the vendored copy in karadoc's MMod: `https://github.com/karadoc/Civ4-MMod/blob/master/Assets/xml/Text/Autolog%20Options.xml`): BUG logs game *events* (tech acquired, city founded/grown/razed, war declared, first contact, attitude changes, GP born, builds completed, etc.) to a text file, formats "Plain | HTML Tags | Forum Tags" — human-readable output aimed at forum session reports, not machine-readable state. Precedent that per-event file writing from Python hooks is safe and long-established, but no schema to reuse. Its loggable-event list is a good checklist of "what the game considers a notable event" if we ever add an `events` (turn-over-turn changes) section to the state schema.
- **CivRealm observation schema** (`https://bigai-ai.github.io/civrealm/advanced_materials/fullgame_observation.html`): the one directly useful structural reference found. Freeciv, not Civ4, and tensor-oriented (map as per-layer M×N grids), but its decomposition transfers cleanly: top-level `map` / `unit` / `city` / `player`, with **common fields for any observed entity vs. extra fields only for player-owned entities** (e.g. any visible unit has position/owner/HP/type, only own units have moves-left/upkeep; any visible city has name/position/owner/size, only own cities have stocks/production/mood), and `player` aggregating diplomacy + government + technology. *Verified against the linked docs page.* That common-vs-owned split is exactly the fog-of-war/visibility distinction our schema needs.
- **CivAgent / "Digital Player" paper** (`https://github.com/fuxiAIlab/CivAgent`, fuxiAIlab): LLM agent playing Unciv (open-source Civ5-like) — conceptually the closest project to our harness side (game state → LLM prompt → decisions). *README verified; it contains no concrete state schema* — the paper describes prompts combining background, turn context, role profile, event log, and JSON-encoded "skills," but field-level detail would require reading the paper/source. Park as a harness-phase reference for prompt structure, not a mod-phase schema source.

## Python event modding tutorials (found while diagnosing turn-numbering behavior)

- **TGA's Python Tutorial** (CivFanatics): `https://forums.civfanatics.com/threads/tgas-python-tutorial.154130/`
  Confirms (independently of our own in-game testing) that `onEndPlayerTurn` fires at the end of the *start* of a turn, not the end of the turn itself, and that both `onBeginGameTurn` and `onEndGameTurn` fire at turn end rather than beginning — matches what we measured empirically. Also recommends a custom event manager over editing `CvEventManager.py` directly (see below), and covers debug `.ini` flags (`HidePythonExceptions`, `ShowPythonDebugMsgs`, `LoggingEnabled`) and log file locations (`PythonDbg.log`, `PythonErr.log`, `PythonErr2.log`).
- **CvEventInterface** (Civilization Modding Wiki): `https://modiki.civfanatics.com/index.php?title=CvEventInterface`
  Documents the recommended pattern for hooking events without editing `CvEventManager.py`: create `CvCustomEventManager.py`, then edit only the top of `CvEventInterface.py` to import it and point `normalEventManager` at your custom class instead of the base one.
- **CvEventManager** (Civilization Modding Wiki): `https://modiki.civfanatics.com/index.php/CvEventManager`
  Reference list of ~90 event triggers. Explicitly notes it's missing firing-order/timing detail beyond the one-line description of each hook — our own in-game instrumentation is more precise than any docs found so far.
- **"How to make a Python mod" thread** (CivFanatics, page 4): `https://forums.civfanatics.com/threads/how-to-make-a-python-mod.374238/page-4`
  Practical discussion of the custom-event-manager pattern; notes that modules needing live game state (`gc.getGame()`, etc.) at import time should be imported from inside an event handler (e.g. `onGameStart`), not at module top-level, since top-level imports run before the game is fully initialized. Doesn't appear to affect us currently (`AdvisorStateWriter` only touches `gc` inside functions, never at import time).
- **Modders Guide to Beyond the Sword** (CivFanatics): `https://forums.civfanatics.com/threads/modders-guide-to-beyond-the-sword.229557/`
  General mod structure/workflow guide. No hot-reload or live-editing technique described for Python changes, and none found anywhere else in the community either. Event-manager-level edits do genuinely require a full game restart. For every *other* module we since found one that works — `execfile` into the live module's `__dict__`; see "Python hot-reload inside the embedded interpreter" above.
- **`onGameStart`/`onLoadGame` — citation is weak, be aware:** the only support found for "re-initialize in both" is one unelaborated forum line from a single poster ("platyping," using `onGameLoad` rather than `onLoadGame`) in `Free Technology granted at a specific Year: a Python solution`: `https://forums.civfanatics.com/threads/free-technology-granted-at-a-specific-year-a-python-solution.493414/`. Not a documented community-known issue — don't cite it as one. Exporting from `onLoadGame` is still correct on its own logic regardless (`onGameStart`'s own docs say "called at the start of the game," which excludes resuming a save).
