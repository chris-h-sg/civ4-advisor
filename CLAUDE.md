# civ4-advisor

## What this is

A setup that lets an AI (Claude) observe game state from **Civilization IV: Beyond the Sword** and give strategic advice. Long-term goal: the AI eventually suggests concrete actions the player executes on its behalf. Current goal, much smaller: get advice-only working end to end, scoped to the **first 50 turns** of a game.

## Why Civ IV

Civ IV exposes a full Python 2.4 scripting layer (the `Cy*` API — `CyGame`, `CyPlayer`, `CyCity`, `CyUnit`, `CyPlot`, `CyTeam`) that the modding community has used for years to read and influence live game state. This lets us extract structured game state directly via the game's own event hooks, instead of relying on screenshots + vision models. The game is turn-based, so latency is a non-issue — no reflex/timing pressure on the AI call.

## Architecture: two independent parts, no shared code

- **`mod/`** — lives inside Civ IV's Python layer. Runs in the game's embedded **Python 2.4** interpreter. Windows-only, tied to the actual game install. Its only job: hook into the game's turn-cycle events and write a snapshot of player-visible game state to a JSON file on disk. (Not `onBeginPlayerTurn` alone, despite the name suggesting "start of turn" — see Design decisions below; the naming is misleading relative to actual firing order.)
- **`harness/`** — a normal external **Python 3** project: **tooling an agent invokes**, not an API client. Reads the state JSON the mod writes and renders it into forms an agent can reason over (starting with the map renderer). No dependency on Civ IV being installed — developable/testable purely against saved samples.

The only contract between the two parts is **the JSON file on disk**. Neither part imports from or depends on the other's code.

**There is no custom API client, and there will not be one** — an agentic coding tool (Claude Code or Cowork) is pointed at this repo plus the game's XML, reads the state files directly, and gives the advice. See the design decision below for what that choice deletes.

## Current phase — what's actually being built right now

The **mod is complete** for the current scope: it exports the full schema and keeps a per-game turn history. **`harness/`'s three planned tools are also built** — `render_map.py`, `run_history.py` and `rules.py` — and the whole setup has now been exercised end to end in two live advisor trials.

One curated sample exists — `samples/baseline-early-game/`, turns 0–43 on default settings, covering first- and second-city placement, fog staleness, rival observation and resource connection. Note its provenance caveat (see that folder's README): five increment-⑤ fields are backfilled on every turn except 40 and 43.

**Everything unbuilt — mod, harness and samples — is queued in `ROADMAP.md`**, with the agent-trial evidence behind each item. That is the single roadmap; this file and the per-folder READMEs describe what exists and why it is shaped the way it is.

Do not implement action execution until explicitly asked — that is a future phase, not current scope.

## Scope for now

- Turns 0–50 only: exploration, first cities, early expansion, early tech/civics. Widened from 1–20, which proved too narrow — a second city, the first population growth and the first unit loss all land after turn 20, so the interesting early decisions were falling outside it.
- **Schema v1 is specified** in `schema/state.schema.json` and **mod-side extraction is now complete against it** — every section is built, so live output validates against the whole document. (Build order and per-increment decisions in Design decisions below.)
- Advice only. No action execution yet.

## Key technical constraints

- **`mod/` targets Python 2.4.** No `json` module (postdates 2.4), no f-strings, no modern syntax. JSON serialization inside the mod must be hand-rolled or use a 2.4-compatible vendored library — never assume the standard `json` module is available here.
- **`harness/` targets modern Python 3.** Normal tooling, `json`, type hints, etc. all fine.
- File writes from the mod go to a temp file, then rename over the target, so the harness never reads a half-written file. Not a fully atomic *replace*, deliberately — see the design decision below.
- The mod must never crash or hang the actual game — it writes a file and returns control, full stop. Everything fragile lives outside it.
- Nothing in this repo holds an API key or talks to a network service. The agentic tool brings its own auth; `harness/` is offline file processing.

## Design decisions already made (don't relitigate without reason)

- File-based IPC over sockets/HTTP — simplest thing that works for a turn-based, single-machine setup.
- **The advice layer is an agentic tool (Claude Code / Cowork) reading these files directly — not a custom API client.** The file-on-disk contract was already exactly what such a tool consumes, so **the mod does not change at all** for this; that is what makes the choice cheap. What it deletes: prompt assembly, retry/error handling, API-key and secrets handling, any chat or UI, and the XML parse-and-cache subsystem (the agent greps the game's XML on demand instead — the files are large, so grep, don't read whole). What it costs: no automatic trigger on end-of-turn (you ask, per turn), and weaker prompt-quality iteration — instructions live in version-controlled markdown, but there is no deterministic prompt to A/B and no automatic log of state→advice pairs. Judged worth it: the interesting engineering is the mod, and the deleted work is all reimplementation of what the tool does natively. Which tool (Claude Code, Cowork, or both) is **not decided** — both just read a folder, so nothing downstream depends on it.
- **`harness/` tools earn their place only where the agent is unreliable on the raw JSON, and they present rather than decide.** The agent reads JSON well, so most of the export needs no tooling; the gaps are spatial reasoning, aggregation across many turn files, and consistent arithmetic over many rows. The planned set and the rejected candidates are in `harness/README.md` — kept there with reasoning so they aren't re-proposed later. The line that matters: a tool that *ranks* city sites moves the strategic judgement into Python and leaves the AI reading out conclusions, which defeats the point; a tool that *shows* a site's worked radius does not.
- **The agent instructions are `harness/AGENT_GUIDE.md`; `harness/README.md` is strictly for developers.** One rule keeps the split: **usage and traps in the guide, reasons in the README** — a guide that argues with itself gets skimmed. The guide names each tool and when to reach for it, since a tool the agent doesn't know about doesn't exist, and asks it to flag where a tool *would* have helped. What the trials validated about that instruction, and why the guide leads with compass direction, are in `harness/README.md` "The agent instructions".
- The turn-50 cutoff is **prompt guidance, not code** — nothing enforces it. It was never going in the mod (keeps the mod dumb, avoids redeploying in-game when scope changes) and there is now no harness request path to put it in either.
- XML rules data (unit stats, building costs, tech tree, civics) is static and lives in the Civ IV install, not this repo. The agent reads it on demand; it is deliberately not parsed, cached, or copied here.
- If/when this becomes a public portfolio repo: never vendor Firaxis SDK headers/binaries or copyrighted game assets — reference them as "install into your own Civ IV directory," don't bundle them.
- Local Civ IV install/Mods folder paths live in `config.local.json` (gitignored, machine-specific — other contributors' paths will differ). `config.local.json.example` documents the expected shape and is committed.
- Real state JSON captured from actual play is called a **sample**, stored in `samples/` (not "fixtures"). **A sample is a whole game run — a folder of consecutive `turn_NNNN.json` files — not a single curated turn.** That follows from the mod keeping per-game history: a run is what the mod naturally produces, and the sequence is the thing worth testing against, since some reasoning only works across turns (below). Each file carries its own `game` setup section, so a run is self-describing and needs no separate metadata.
- Mod name is `civ4-advisor`, matching the repo. Its `.ini` lives at `mod/civ4-advisor.ini`. It was originally kept minimal (just `Name`/`Description`) because explicit flags like `AllowPublicMaps = 0` blocked "Play Now"/"Custom Game" (no map scripts available), so everything else was left to fall back to engine defaults rather than guessing at "safe" values. **The game itself now writes the full flag block back into the file**, with `AllowPublicMaps = 1` and every other flag at its default — so the committed `.ini` is the expanded form the engine produces, not a hand-authored one. That is the same *effective* configuration the minimal file had; it is checked in as-is so the game stops showing the file as modified after every run. The original hazard was the value, not the presence of the key: don't set `AllowPublicMaps = 0`. Reverting to the minimal form is pointless — the engine will just rewrite it.
- `mod/` is the source of truth; it's deployed into the real Mods folder via a **directory junction** (`mklink /J`), not a copy step and not a symlink (symlinks need admin privileges on Windows; junctions don't). Edits in the repo are live in-game immediately.
- A mod only needs to ship the specific files it overrides — not a full copy of the base game's `Assets/Python/` tree. Currently that's `Assets/Python/EntryPoints/CvEventInterface.py` (base file, only its event-manager import/instantiation changed), `CvCustomEventManager.py` (new), and `AdvisorStateWriter.py` (new), plus `LocalConfig.py` (new, gitignored — `LocalConfig.py.example` is committed in its place).
- **Event hooks go through `CvCustomEventManager.py`, subclassing the base (imported, not copied) `CvEventManager.CvEventManager`** — not a modified copy of the base file. This is the community-established pattern (see `REFERENCES.md`): `CvEventInterface.py` (the real C++ entry point) only has its top changed, `import CvCustomEventManager` / `normalEventManager = CvCustomEventManager.CvCustomEventManager()`, the four functions below untouched. Each override calls the superclass method first to preserve base behavior. Rationale: a full copied `CvEventManager.py` is 1000+ lines with a handful changed — a lot of surface area to review and easy to drift from the original; `CvCustomEventManager.py` contains only what we added. Does **not** solve the hot-reload limitation below — the engine still holds a reference to an instantiated custom-manager object either way.
- **`onBeginPlayerTurn`/`onEndPlayerTurn` do not bound the player's actual interactive turn, despite the naming** — no hook fires during the player's actual interactive play. `onBeginPlayerTurn(N, human)`/`onEndPlayerTurn(N, human)` only fire back-to-back once "End Turn" is clicked (matching turn N, the one just concluding, no numbering offset), followed by the same pair for every AI civ in player-ID order, only then followed by `onBeginGameTurn(N)`/`onEndGameTurn(N)` — all at turn *end*, not beginning. Confirmed via in-game instrumentation and independently corroborated by TGA's Python Tutorial (see `REFERENCES.md`). Net effect: no hook fires at the exact moment the player gains fresh control for a new turn — hence the export strategy below.
- **State export uses `onGameStart` + `onLoadGame` + `onEndGameTurn` — not `onBeginPlayerTurn`.** `onGameStart` fires once, before the game's true first turn has been played (no numbering adjustment needed). `onLoadGame` covers the same case for a resumed save, since `onGameStart` only fires for a new game. `onEndGameTurn` fires *last* in a round's processing (after human + every AI civ) — the freshest available proxy for "what the player is about to see" once they silently regain control — using `iGameTurn + 1` since the round it reports just finished. All three share a common `_exportState` helper on `CvCustomEventManager`, wrapped in `try/except` per the "mod must never crash" constraint above (it logs rather than swallowing silently — see below). **Every file is numbered for the turn *about to be played*** — `onGameStart`/`onLoadGame` pass `getGameTurn()`, `onEndGameTurn` passes `iGameTurn + 1`. Two consequences worth knowing before reading a run: a run starts at **`turn_0000`** (confirmed live), which is the state before turn 1 is played and therefore the snapshot the first-city decision is actually made from — the most valuable file in the run, not an off-by-one artifact; and **loading a save re-exports that turn, overwriting its file**, so file mtimes within a run are not monotonic (order by filename, never by mtime) and `meta.trigger` reads `onLoadGame` rather than `onEndGameTurn` for any turn that was resumed.
- Live per-turn state is written under `state/` at the repo root (gitignored — regenerated live output, distinct from the curated, committed `samples/`), one file per turn (`turn_0001.json`, `turn_0002.json`, ...) inside a per-game subfolder — a full game's history is kept rather than each turn overwriting the last.
- **Per-game folders are named `{leader}_{gameId}`, where `gameId` is a synthetic ID the mod *writes* into `CvGame.scriptData` — not a value read from the engine, because no readable persistent game ID exists.** `_gameId()` in `AdvisorStateWriter.py` generates one from `time.time()` the first time `getScriptData()` comes back empty, then writes it back once; every later load of that save, including a full game restart, returns what was written, which keeps the folder stable for the life of the game rather than just the session. **A deliberate, judged-safe exception to the mod otherwise only ever reading state** — the field is unused free-form storage with no gameplay effect. Leader name is prepended only for human readability; it plays no role in uniqueness. `LocalConfig.STATE_DIR` is the root directory these folders live under, not a single file path. Why reading was a dead end (no UUID, no save identity, no readable map seed) and why the read-only alternative was rejected are in `REFERENCES.md` "No readable persistent game ID".
- **The turn history is the player's memory, and reasoning across it is a first-class use of the export — not just backup.** Each snapshot is deliberately forgetful, mirroring the engine: `foreignUnits` only reports currently-visible units, so a rival's Axeman seen on turn 14 is simply absent from turn 15. The *sequence* restores what a human player retains — spotting that Axeman at all implies Bronze Working, and that inference stays valid long after the unit drops out of sight. Same for tracking rival city growth, border expansion, and where their units came from. This is honest, not a fog leak: reading turn 14's file gives exactly what the player could see on turn 14, nothing more. The rule it needs is a boundary, not a restriction — **a past turn is evidence about the past, from which you infer; only the latest turn is the current state.** A city that was size 3 on turn 14 is not size 3 now, and a tile's `visibleNow` was answering a question about turn 14. Carrying a stale value forward as fact is the failure mode here, and it will look plausible.
- **Paths can't be derived at runtime inside the embedded interpreter — both automatic routes are measured dead ends.** `__file__` is reported relative to the engine's own `Assets/Python` search root rather than the real physical location (even through the deployment junction), and no `sys.path` entry survives `os.path.isfile`. So machine-specific paths come from `mod/Assets/Python/LocalConfig.py` (gitignored — `LocalConfig.py.example` is the committed template), a plain Python module the mod imports directly rather than a parsed config format, since Python 2.4 has no `json`. It holds `STATE_DIR` plus the optional `MOD_PYTHON_DIR` and `LOG_TIMINGS`. A missing `LocalConfig.py` is handled, not fatal: every setting falls back to a default, so `getTurnFilePath()` returns `None` and `writeStateFile` no-ops.
- **`reload()` silently does nothing in this interpreter; hot-reload works via `execfile` into the live module's `__dict__`** — `_refreshStateWriter()` in `CvCustomEventManager.py`, using `MOD_PYTHON_DIR`. Measured in-game in both directions; the measurement and the ruled-out causes are in `REFERENCES.md`. Consequence: the three mod Python files have **different edit rules**, and that asymmetry is exactly what makes a broken reload hard to notice, since a restart always works and masks it. `AdvisorStateWriter.py` — applies next export. `CvCustomEventManager.py` — always needs a restart (the engine holds an instance built from the old class; nothing can re-class it, and no community workaround exists). `LocalConfig.py` — needs a restart too, being imported *by* `AdvisorStateWriter` and so served from the import cache.
- **State schema v1 is formally specified as JSON Schema (draft 2020-12) at `schema/state.schema.json`**, with a synthetic always-valid example at `schema/state.example.json` — illustrative, deliberately NOT in `samples/`, which stays reserved for real captures. The mod (Python 2.4) can't consume the schema; it's the human-readable contract reference now and the harness-side validator later. `meta.schemaVersion` bumps on breaking changes. Designed after surveying prior art (nothing reusable exists for Civ4; CivRealm's observed-vs-owned decomposition borrowed — see REFERENCES.md "State-extraction prior art").
- **Schema v1 design choices:** enum-like values are the game XML's `Type` keys as strings (`TERRAIN_GRASS`, `UNIT_SCOUT`) so state joins against XML rules data with no mapping tables; game-computed derived values (tile yields, city per-turn rates, research turns-left) are exported rather than re-derived in the harness; strict player-visibility honesty (tiles if ever revealed with a `visibleNow` staleness flag, foreign units only on currently-visible tiles, resources via the team-aware getter so tech-hidden bonuses don't leak); full snapshot every turn, no diffs (mod stays stateless); top-level sections `meta/game/player/units/cities/wonders/map/contacts/foreignUnits/foreignCities`. `player.goldPerTurn` is the net treasury delta and `player.beakersPerTurn` the modifier-inclusive `calculateResearchRate` — Civ4 applies hidden bonuses (met-civs-know-tech, known-OR-prereqs, +1 base beaker) to the research *rate*, and overflow makes `turnsLeft` ≉ cost/rate right after a tech completes (verified in SDK source — see REFERENCES.md "Research-rate mechanics"). Build order: ① game+player, ② units+cities, ③ map.tiles, `cities[].workedTiles` and the `game` setup fields, ④ contacts+foreignUnits+foreignCities, ⑤ `player.bonuses`/`cities[].bonuses`/`cities[].coastal`/`wonders`, ⑥ `cities[].productionFromHammers`/`productionFromFood` — **all done**. New extraction logic goes in `AdvisorStateWriter` (hot-reloadable), not `CvCustomEventManager` (isn't) — the event manager passes only turn/player/trigger through to `AdvisorStateWriter.buildState`.
- **Export what the game itself computes and displays, read the way the game's own Python reads it.** Concretely: units export `moves` (`baseMoves()`, total per turn) and NOT moves-remaining, because `movesLeft()` is reset in `CvUnit::doTurn()` *after* our export hook, so it always describes the round that just ended (a warrior that had moved exported `0` — schema changed from `movesLeft` on the strength of that live capture); `productionNeeded` is `null` for both an empty order queue and a process, since the engine reports `MAX_INT` for both; city rates use the city screen's own arguments (`foodDifference(True)`, `getCurrentProductionDifference(False, True)`, `unhappyLevel(0)`, `badHealth(False)`, `getCulture(owner)`); `research.progress` adds the modifier-scaled overflow term the research bar adds, and `research.cost` is the team cost, not the raw XML one. Two knock-on effects worth knowing: `foodPerTurn` reads 0 rather than negative during disorder *and while a food build is queued*, and `productionPerTurn` carries one-off overflow the turn after a build completes, so it isn't a steady-state rate — a caveat its two halves (increment ⑥) inherit. Per-method detail and citations in `REFERENCES.md`.
- **`units`/`cities` are sorted by engine ID before export.** The engine's `firstUnit`/`nextUnit` and `firstCity`/`nextCity` cursor order isn't documented as stable, and unsorted output would produce spurious turn-to-turn diffs — same rationale as the sorted dict keys. Iteration and filtering (`isDead()` for units, `isNone()` + owner check for cities) mirror the base game's `PyHelpers.getUnitList`/`getCityList`.
- **While a schema section was unimplemented it was omitted from mod output, never emitted as an empty list** — an empty `contacts` array can't be distinguished from a player who has genuinely met nobody. That rule applied to whole *sections*; an implemented section that is legitimately empty (a player with no cities yet) is written as `[]`, which is honest. **Now that increment ④ has landed nothing is omitted, so `[]` is unambiguous on its own and output validates against the whole schema** — `mod/tests/test_state_writer.py` checks the full document rather than section-by-section subschemas, which is also what makes the schema's top-level `required` and `additionalProperties: false` bite. Distinct from field-level omission inside `map.tiles`, `units` and `foreign*`, which means "this field has its default" — see below. That test execs the real `AdvisorStateWriter.py` under Python 3 with the `Cy*` API and Python-2 builtins mocked, so extraction logic can be checked without launching the game — it verifies behaviour only and cannot catch Python 2.4 syntax violations.
- **Section builders take a single `_Context` object** (`gc`/`game`/`cyMap`/`player`/`team`/`playerId`, resolved once in `AdvisorStateWriter`) rather than threaded parameters — adding a section shouldn't mean re-plumbing signatures through `buildState` and every builder.
- **Failed exports are logged, not just swallowed.** `_exportState` never re-raises (the mod must not block a turn), but it `pyPrint`s the traceback to `PythonDbg.log` — a silent no-write is otherwise indistinguishable from the mod not being loaded at all, and leaves the previous turn's file in place looking current. The logging call is itself wrapped in `try/except`, since it must not turn a failed export into a crash.
- **The temp-file-then-rename write is not a fully atomic replace, deliberately.** Windows `os.rename` fails when the target exists and Python 2.4 has no `os.replace` (`ctypes` only arrived in 2.5), so the old file is removed first. That leaves a brief window where the state file is *absent* but never one where it's *half-written* — a missing file is detectable and retryable by the harness, a truncated one parses as garbage.
- **State is written in binary mode as UTF-8.** Game strings (city names, from increment ② onward) come back as wstrings and make the whole rendered document unicode; binary mode also stops Windows rewriting `\n` to `\r\n`, so output bytes are exactly what was serialized (needed for the byte-identical/diffable property above). **Confirmed live**, not just in tests: a real capture containing the city `Päris` round-tripped intact through `getName()` → hand-rolled serializer → encode → binary write.
- **State output is pretty-printed with sorted keys** (2-space indent; short containers stay inline), not compact — the file is read by humans comparing it against the game UI, and sorted keys make turn-to-turn diffs meaningful given Python 2.4 dicts have no insertion order.
- **`map.tiles` is per-tile JSON objects, one per line, with default-valued fields omitted — and the mod never renders a map grid.** Pruning is the win that matters; column-oriented and `columns`+rows layouts both measured *larger* than pruned objects as well as being worse to diff and harder for a model to index. An ASCII grid is far smaller and is genuinely the better *prompt* form, but **rendering is a harness concern** — grid-from-objects is a trivial derivation, objects-from-grid is impossible, and presentation logic does not belong in the process that must never crash the game. Bounding the exported region was rejected as a fog-of-war lie in the other direction. Measurements in `REFERENCES.md`. That decision survived the move to an agentic tool unchanged; only the meaning of "harness" changed — it is now a script the agent runs, not a service.
- **The map renderer is a `harness/` tool the agent invokes with a chosen view, not a fixed prerender.** Measured on a real turn-12 capture: 939 chars of ASCII grid against 27,638 for the same JSON (~29×), and the grid makes adjacency free instead of derived. Three rules it is built on. **(1) The grid complements the JSON, never replaces it** — it is lossy by design, so the agent orients on the grid and verifies specific tiles against the JSON before committing to a decision. **(2) Named views, not orthogonal flags** (`--view settle`, not `--yields --owners`): flags push the "what matters for this decision" judgement onto the agent on every call, where it will be re-derived slightly differently each session; a named view encodes it once in tested code. Two parameters at most — which region (whole map, or cropped around a point) and which view. **(3) Rendering only, never a query language** — no filter/sort/top flags; non-spatial questions go to the JSON, which the agent reads fine, and wanting a filter flag is the signal that it should. Output is generated on demand and never committed: a stale grid that disagrees with the JSON misleads confidently with no way to notice.
- **`y` increases SOUTH in the exported data (schemaVersion 2), so grid rows must be rendered in *ascending* y.** Get this wrong and north lands at the bottom, mirroring every directional judgement silently — "settle north toward the grassland" points at tundra. Confirmed against a real capture rather than assumed: on the baseline run, tundra sits at y=40 (near the pole) while the jungle band sits at y=22–29 (nearer the equator), i.e. pole-to-equator banding as y rises. This is the clearest argument for the renderer being tested code rather than something the agent re-derives per session — a re-derivation gets it right most of the time and inverted the rest, with no signal either way.
- **Which fog states a view must distinguish depends on the decision, and it is load-bearing for military views specifically.** `foreignUnits` only reports units on *currently visible* tiles, so a view that flattens unrevealed / fogged / visible renders an unobserved region as "no enemies" and will get a unit killed. City-placement views don't need fog at all — there the relevant facts are tile ownership and the positions of existing cities (Civ4 enforces a minimum distance between cities, making that a hard constraint rather than context). The exact view set is **not decided yet**; it is the first thing the renderer's own session is meant to propose from the schema.
- **Field omission means something different from section omission.** A missing *section* used to mean "not built yet" (above); a missing *field* means "it holds its documented `default`". In `map.tiles` only `x`/`y`/`terrain`/`yields` are unconditional; `damage` is omitted from any undamaged unit, ours or a rival's; `capital` from any foreign city that isn't one. It costs nothing in honesty, because every default is a value that was already ambiguous — a missing `bonus` has always meant both "no resource" and "no revealing tech yet". The one real cost: in an old capture a field added later is indistinguishable from one that defaulted, which is what `meta.schemaVersion` is for. **`meta.schemaVersion` stayed at 1 through increment ④** — every ④ change was additive, nothing consumed v1 yet, and v1 only became an accurate description of real output rather than a target. It first bumped, to 2, for the y-axis inversion below — see that bullet for what finally consumed it.
- **Fog of war in `map.tiles`: `improvement`, `route` and `owner` use the revealed getters; everything else uses live ones because no revealed variant exists.** Those three are the only things the engine remembers per team; for the rest it has no memory to return and reads live in its own tooltip too, so a live value here is the same call the game makes rather than an approximation. `bDebug` is `False` everywhere — `True` bypasses to full-map truth under debug mode. Facts, citations and the one leak this inherits are in `REFERENCES.md` "Plot/map API semantics".
- **Tile `yields` are the displayed yield, `calculateYield(y, bDisplay=True)`** — which is also the fog-honest choice, since it uses the revealed improvement/route/owner internally. It inherits two engine quirks worth knowing before reading a capture (deep ocean reads `[0,0,0]`; unowned tiles get the active player's trait bonuses applied); both are documented at the `yields` field in the schema.
- **`buildState` refuses to run at all when the exported player isn't the active player** (`_requireActivePlayer`), because two getters silently answer for `getActiveTeam()` rather than any team we can pass and there is no API to ask either about a specific player: `calculateYield(bDisplay=True)` for tile yields, and `CyUnit.getVisualOwner()` — which takes no team argument in the Python layer — for foreign unit ownership. The assumption holds in single player but nothing enforces it, so the mod asserts instead of trusting it; `_exportState` turns that into a logged traceback and no file. It lives in `buildState` rather than in `_buildMap`, where it started: it's a property of the whole export, and a guard that lives inside one section is a guard the next section silently does without — which is exactly what nearly happened when ④ added the second active-team dependency.
- **`plotType` is one field (`PLOT_PEAK`/`PLOT_HILLS`/`PLOT_OCEAN`, omitted for `PLOT_LAND`), not three booleans** — peak/hills/water/flat are a single engine enum, so separate flags would be more verbose *and* able to encode states that cannot exist. Read via the `isPeak`/`isHills`/`isWater` predicates, because the individual `PlotTypes.PLOT_*` constants are never referenced in the base game's own Python and so are unverified. `lake` and `freshWater` stay separate booleans — orthogonal, and not derivable from anything else exported.
- **`river` is a boolean only.** Everything in scope keys off "is this tile on a river"; edge geometry only matters for movement cost and the river-attack modifier, both action-phase concerns, and would be incomplete at the revealed boundary anyway. Purely additive later — but read the `isNOfRiver` naming trap in `REFERENCES.md` first.
- **Worked tiles live on `cities[].workedTiles`, not on map tiles** — honest by construction, since we only ever iterate our own cities and a rival's cannot leak, and ~10x cheaper. The map-side alternative would have meant hand-reimplementing `CvPlot::isVisibleWorked`, which the engine has but does not expose to Python.
- **The AI's city-site "blue circle" was considered and dropped on cost** — reasoning kept in `REFERENCES.md` so it isn't re-litigated from scratch.
- **`_Record`, a dict subclass, renders one tile per line and leads with `x`/`y`.** Most real tiles exceed `_MAX_INLINE_WIDTH`, so without it the section is a ragged mix of one-liners and exploded objects; a marker rather than a bigger global width, which would also rewrite how every existing section renders. Leading keys keep the coordinates off the end of the line without weakening diffability: what that needs is a *fixed* key order, and a constant tuple followed by a sort is exactly as fixed as a sort alone.
- **`game` carries the setup the player chose, never the generated map's statistics.** The setup fields join against XML to give an expectation about unexplored map (climate implies hills and desert, sea level implies water), and `options` punches above its weight for our scope, since the barbarian settings change turn-1–20 advice more than almost anything else in the file. The excluded getters sit right beside the safe ones on the same objects; they're listed in `REFERENCES.md` and raise in the test mocks, so the line stays enforced rather than remembered. `totalCivs` is `countCivPlayersEverAlive` precisely because "ever alive" is constant and so leaks nothing.
- **Export timing is measured unconditionally and reported conditionally** — the slow-map warning can't be lost by forgetting a config flag, while the full per-section breakdown needs `LOG_TIMINGS` in `LocalConfig.py`. Kept permanently rather than measured once and deleted, since the cost grows with the revealed area. There is deliberately **no** automatic degradation: a silently truncated map is indistinguishable from genuine fog, which is far worse than a slow export. Measured figures in `REFERENCES.md`.
- **Increment ⑤ exports the *inputs* a "what can this city build?" answer needs, deliberately not the answer.** The prompting question was whether to export `canTrain`/`canConstruct` per city. No: that list is large, near-static, duplicates the XML, and moves judgement into the mod. But "derive it in the harness from tech + resources + already-built" doesn't close either, since the real `canConstruct` gates on more than those — so the gap-filling inputs get exported and the derivation stays a harness concern. New: `player.bonuses` (grouped, plus empire-wide counts), `cities[].bonuses` (grouped, membership only — quantity is an empire fact the engine doesn't model per city), `cities[].buildings`, `cities[].coastal`, and a top-level `wonders`. Still absent by choice: the buildable list itself, and the engine's `bTestVisible` "shown but greyed out" distinction, which the harness must reconstruct rather than get free.
- **Bonus groups are `strategic`/`happiness`/`health`, and `strategic` is derived, not flagged.** There is no `bStrategic` in the XML and `CvBonusInfo` exposes no reverse index, so it means "some unit or building names this as a prerequisite", swept from the unit/building infos. A bonus lands in exactly one group, strategic winning ties, so the lists partition rather than overlap. `coastal` is exported rather than derived because the engine's test is adjacency to a water body of a minimum size, not "is a neighbour water" — a city on a small pond isn't coastal. See REFERENCES.md "Connected resources and wonder availability".
- **`wonders` is the only section carrying information the player didn't observe themselves, and it is public rather than leaked.** Whether the Pyramids are still available depends on a rival we may never have met, nothing else in the export can imply it, and without it advice will recommend a wonder finished elsewhere ten turns ago. The game's own Info screen settles that it's public: it lists every world wonder built anywhere and gates **only the builder's identity** on `isHasMet`, rendering an unmet builder as "Unknown"; a global popup fires for everyone on completion. So the section exports *that* a wonder is gone and never *who* built it or where — the flat-list shape leaves nowhere to put an owner. `built` is world wonders gone globally; `national` is our own one-per-civ wonders, rivals' being neither public nor relevant since they use nothing up for us.
- **`cities[].buildings` uses `BUILDING_` keys while `wonders` uses `BUILDINGCLASS_` keys, and the mismatch is deliberate.** A wonder's limit is a property of the *class*; what stands in a city is an actual *building* with its own effects, and a civ's unique replacement shares a class without being the same thing. The two are **not interconvertible by string surgery** — 28 stock buildings have a differently-named class, several many-to-one (`BUILDING_COAL_PLANT`/`HYDRO_PLANT`/`NUCLEAR_PLANT` are all `BUILDINGCLASS_FACTORY`) — so deriving one from the other will be quietly wrong; export a separate field if a class key is ever wanted. Expect `BUILDING_PALACE` in the capital from turn 0, in both this and `wonders.national`.
- **`meta.schemaVersion` stayed at 1 through increments ⑤ and ⑥.** Every change was additive — no existing field changed meaning — and nothing consumed the version yet. See below for the first thing that did.
- **`meta.schemaVersion` bumped 1 → 2 to invert the exported y-axis: `(0,0)` is the NORTHWEST corner and `y` increases SOUTH, opposite the game engine's own y-up space.** Ten agent trials read coordinates correctly and then narrated north/south backwards — all ten, x never once wrong — so the export now matches the screen/image/matrix prior every model brings instead of fighting it. The transform is `y = mapHeight - 1 - y`, applied once in `AdvisorStateWriter._invertY` just before `buildState` returns, so no section builder is touched. Every `harness/` entry point hard-refuses any file that isn't schemaVersion 2, which is what makes a stale v1 file fail loudly instead of rendering mirrored. **Action execution will need exactly one inverse, at the one boundary where a coordinate goes back to the engine** — a missed inverse there is a silently mirrored move order. Full trial evidence, the rejected `row`/`col` rename, why this is a judged exception to "export what the game computes", and the sample migration are in `REFERENCES.md` "The y-axis inversion".
- **Increment ⑥ exports the food and hammer halves of city production as two always-present fields, because the split is unrecoverable from a single turn's file.** `productionPerTurn` folds food into hammers while a Settler or Worker is queued (and `foodPerTurn` then reads 0), so `rules.py` had to *infer* which builds were food-fed — correct for food builds, wrong for ordinary ones sharing a city, which inherited food they'd never get and were flagged "optimistic" rather than corrected. So `cities[].productionFromHammers`/`productionFromFood` are exported, summing to the unchanged `productionPerTurn`. **The subtraction is exact, verified in `CvCity.cpp` rather than assumed**: `bFoodProduction` gates one additive term and leaves the hammer expression identical, and the engine performs this very subtraction itself in `getProductionBarPercentages` to size the city screen's two-tone bar — the game's own decomposition. A building never consumes food, but `bFood` in the XML is not the whole gate (a Police State civic makes military units food-fed too), so the field is authoritative where the XML isn't. Two fields rather than one keep the sum a checkable invariant instead of harness arithmetic. Details and citations in `REFERENCES.md`.
  - **Only `turn_0040`/`turn_0043` of the baseline run are genuine; the other 41 city-bearing turns are backfilled by derivation** — same formula, rendered through the mod's own serializer so the diff is pure insertions. Reasoning, validation (48/51 agreement against an independent model) and the one unsound case are in `samples/README.md`'s provenance caveat. Cost accepted knowingly: `rules.py`'s fallback path now has no sample coverage, and the sweep test's sum invariant is vacuous on derived turns — `test_the_backfill_derivation_reproduces_the_genuine_turns` is the one that actually checks anything, against t40/t43.
- **Increment ⑦ exports unit combat state — `level`, `experience`, `experienceToNextLevel`, `promotions`, `promotionsAvailable`** — the first live advisor trial had a scout take two promotions from a Lion fight the agent couldn't see; it only knew because the player mentioned it. Same "export the inputs, not the verdict" rule as bonuses/buildings. All five fields are field-omitted at their default (a fresh unit is the common case), and the last two are mutually exclusive by construction — a unit never shows both `promotionsAvailable` and `experienceToNextLevel` at once, since the engine has no single call for either and both re-derive the same level-cost formula. Full API verification, the formula, and the mutual-exclusivity rationale are in `REFERENCES.md` "Unit combat state".
- **`units[].damage` now predicts the value AFTER this turn's heal, rather than the raw, one-heal-tick-stale value `CyUnit.getDamage()` holds at export time** — same staleness mechanism as the `moves`/`movesLeft` fix above (`CvUnit::doTurn()` heals in the same pass that resets moves, after the export hook fires). Unlike `moves`, there was no live equivalent to fall back to (`CyUnit` exposes no `healRate()`), so the post-heal value is *predicted* in `AdvisorStateWriter._healRate` from the engine's own `CvUnit::healRate()` formula, reconstructed component-by-component and verified against the BTS SDK source. **One acknowledged, permanent gap**: a city's building-derived heal bonus (`CvCity.getHealRate()`, e.g. an Aqueduct) has no Python binding, so a garrisoned unit there heals faster in reality than this predicts. `foreignUnits[].damage` stays live-read, deliberately not run through this prediction. Full derivation and citations in `REFERENCES.md` "Unit heal-rate reconstruction". **`meta.schemaVersion` deliberately did not bump for this** — a considered call, not an oversight: unlike the y-axis flip above, migrating the existing samples would mean re-deriving a predicted value per damaged unit per turn rather than applying a pure mechanical transform, and the field still answers the same question ("how hurt is this unit") on both sides of the change. Revisit if a future `damage` (or other field) change needs a hard floor enforced in the harness the way the y-axis one did.
- **Increment ④ added two fields and changed no structure** — unlike ③, which rewrote the schema. The API supported `contacts`/`foreignUnits`/`foreignCities` as originally specified; `foreignUnits[].damage` and `foreignCities[].capital` are the only additions. What ④ mostly produced is *documentation of why each field is safe*, written into the schema descriptions rather than buried in code comments, because these are the sections where a plausible-looking simplification is a fog-of-war leak. All of it has since been confirmed in live play — see REFERENCES.md "Confirmed in live play".
- **Barbarians are in `foreignUnits`/`foreignCities` and deliberately out of `contacts`, and that exclusion is load-bearing rather than cosmetic.** The barbarian team declares war on every civ team in `CvGame::initDiplomacy` and `CvTeam::declareWar` calls `meet()`, so `isHasMet(BARBARIAN_TEAM)` and `isAtWar(BARBARIAN_TEAM)` are **both true from turn 0** — a loop written on `isHasMet` alone reports a barbarian contact, at war, in every export from turn 1. The filter is the base game's own (`isAlive` / not `isBarbarian` / not `isMinorCiv` / `isHasMet`). Their units and cities, by contrast, are the main military fact of turns 0–50 and belong in the file. `attitude` is the five-bucket UI value and cannot be more: the numeric `AI_getAttitudeVal` is not in the Python API at all.
- **The foreign sections iterate each player's own unit/city lists, never a plot sweep.** For units that is the base game's military-advisor pattern, bounded by unit count rather than 4368 plots. For cities it is the *only* correct route: `CyCity.isRevealed(team, False)` is a per-city flag **stricter** than the tile being revealed — a city founded on a tile you revealed long ago but cannot currently see is not revealed to you — whereas `plot.getPlotCity()` is live truth and would surface exactly those. `CyPlot.getPlotCity`/`isCity` raise in the test mocks so that folding ④ into `_buildMap` for speed fails loudly instead of leaking quietly.
- **Units are visibility-gated and forgotten; cities are reveal-gated and persist.** A unit vanishing between exports means "out of sight", not "destroyed" — the engine keeps no memory of enemy positions and neither do we. Invisibility is nearly a no-op this early but is honoured because it also covers cargo, which the map doesn't draw either; owner is `getVisualOwner()` so a hidden-nationality unit is never unmasked by the export. Cities export the live `name`/`population`/`capital` the engine paints on the nameplate with no visibility gate, while it deliberately gates the food and production bars beside them on `canBeSelected()` — so we take exactly what the game shows on a fogged city and nothing of its insides. `visibleNow` is **not** duplicated here: a revealed city always sits on a revealed tile, so the harness joins `x`/`y` against `map.tiles`. (The capital star was initially reported as *not* shown, from reading only the billboard icon-string builder; `CvCity::isStarCity` is the dedicated renderer hook and is the answer. "I checked the obvious builder" is not the same as "I checked".)
- **Rivals' objects get their own tier of test tripwires**, ④ being the first increment to touch them: a rival `CyPlayer` raises on gold/research/civics/counts/power, a rival `CyCity` on every city-screen internal, a rival `CyTeam` on *everything* (nothing should ever fetch one — `isHasMet` is symmetric, so the relation is asked of our own team, and a rival `CyTeam` is precisely the object that would hand over their techs), and `CyUnit.getOwner` raises so `getVisualOwner` is used.
- **`Logs\PythonDbg.log` only updates continuously if `LoggingEnabled = 1` is set in `CivilizationIV.ini`** (default `0`) — with it off, most log files only get written once during initial startup and never again, even though the process keeps running and dispatching events. `HidePythonExceptions` in the same file only suppresses the in-game popup, not the log.
