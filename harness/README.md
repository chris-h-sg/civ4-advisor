# harness/

External Python 3 project: **tooling an agent invokes**, not an API client.

Reads the state JSON written by `mod/` and turns it into forms an agent can reason over. There is no Claude API client here and there will not be one — an agentic coding tool (Claude Code or Cowork) is pointed at this repo plus the game's XML and produces the advice itself. Root `CLAUDE.md` has the reasoning and what that choice deletes.

> **This README is for developers** — design rationale, measured findings, and the boundary that keeps this folder from growing into something else. The advising agent reads **[`AGENT_GUIDE.md`](AGENT_GUIDE.md)** instead.
>
> **Usage belongs in the guide; reasons belong here.** A paragraph here explaining how to invoke something is in the wrong file, and so is a line there justifying a design choice.

## Constraints

- Modern Python 3 — nothing inherited from `mod/`.
- Offline file processing. No network calls, no API keys, no secrets.
- No dependency on Civ IV being installed. Developable and testable against saved runs in `samples/`.
- Take a state-file path as an argument. `mod/` writes one file per turn into a per-game folder under `state/` — don't hardcode a path or a naming scheme.
- Output is generated on demand, never committed. A stale rendering that disagrees with the JSON misleads confidently with no way to notice.

## Running these

Tools take no setup — run them directly with the system Python:

```
python harness/render_map.py state/<game>/turn_0007.json --view settle
```

That is a constraint, not a convenience. An agent running one mid-session will not think to activate a venv first, so a tool that needs one fails with an `ImportError` and turns a strategy question into an environment-debugging detour. **Tools are stdlib-only**, and a proposed dependency is a reason to reconsider the tool.

Tests are the exception and may use dependencies; `harness/requirements.txt` covers those (`pytest` plus `jsonschema`, which `mod/tests/` needs to validate against the schema). Run from the repo root:

```
python -m venv .venv
.venv\Scripts\activate
pip install -r harness/requirements.txt
python -m pytest harness/tests mod/tests
```

## Tools

### `render_map.py` — the map renderer

```
python harness/render_map.py <state.json> [--view NAME] [--around X,Y] [--radius N] [--brief]
```

Five views — `settle`, `explore`, `military`, `yields`, `worker` — each cut to one decision, plus a `--around X,Y` site report. Usage is in `AGENT_GUIDE.md`; the reasoning is below.

Renders are generated on demand and never committed — a stale grid that disagrees with the JSON misleads confidently with no way to notice.

<details>
<summary><b>Design notes</b> — why the views are cut this way</summary>

**A symbol means the same thing in every view.** Each render opens its legend with a `SHARED SYMBOLS` block identical across all five, then adds only what is specific to that view. The column a glyph sits in says what *kind* of fact it is — that is what each legend's `cell = [...]` line is for — but no glyph ever changes meaning between views. Reuse *across columns* is allowed only where the two roles are the same concept: `~` ocean terrain and sea access, `*` resource and (in `worker`) still-unimproved resource, `?` goody hut in both columns that can show one. Those three pairs are enumerated in a test, so adding a fourth is deliberate rather than accidental.


**One fact per column, never a priority rule.** Tile facts coexist freely: grassland *hills* with *forest*, a *resource* and *fresh water* is one ordinary tile, not a corner case — 9 of 266 tiles in the baseline run at t40 carry both a resource and a feature. When facts share a slot the loser is **invisible**, not abbreviated, and nothing in the output hints that anything was dropped. So each view gives every fact it cares about its own column, and which facts get one is exactly what distinguishes the views: `settle` splits feature / resource / water / coast; `worker` splits feature from what is built, because clearing jungle is itself a worker order and stays true under an improvement; `military` splits feature from territory, since forest and jungle are +50% defence and hills +25%. Relief rides on the terrain letter's case, and `^` drops a peak's base terrain because a peak is impassable and unimprovable.

**Full cross-column glyph uniqueness was considered and rejected.** An audit of every glyph the renderers can emit found 62 in use with a dozen ASCII printables still free, so scarcity was never the constraint — but only one pairing carried genuinely unrelated meanings (`%` as both ice and a water state), and that one was fixed by moving ice to `I`. Making the remaining overlaps unique would have cost the mnemonic improvement letters — `F` farm, `M` mine, `P` pasture, `Q` quarry — replacing 14 guessable symbols with arbitrary punctuation, in the one view that already carries the most glyphs. The column disambiguates instead, and every legend states its own `cell = [...]` map, which is a stronger guarantee than uniqueness because it keeps holding when a 15th improvement is added. The property worth having is the cross-*view* one: an agent switching views carries meaning between renders, and never carries meaning between columns of the same cell.

**`settle`'s marker column answers one question, positively.** `A` you may found here · `x` a city within `MIN_CITY_RANGE` · `]` inside a rival's border · blank means the terrain rules it out, which column 2 already names. Availability is marked rather than left blank because the two failure directions are not symmetric: reading water as available is caught instantly by the terrain glyph, whereas reading an available tile as blocked **silently loses a site**. Terrain-unfoundable tiles stay blank on purpose — once `A` is positive, blank is unambiguous, and marking water too would spend ~23% of all cells restating column 2. The settler glyph `S` covers the marker on the one tile most worth knowing about, so the `YOUR SETTLERS` block states that tile's legality in words instead.

**The water column carries three independent bits, and river is not one of fresh water.** River, non-river fresh water (a lake or an oasis) and sea access are separate facts, so the grid encodes all six reachable combinations rather than ranking them: `_` neither · `:` fresh, no river · `/` river · `~` sea only · `%` sea + fresh but no river · `&` sea + river. River beats lake in the two combined states. **What a river is worth is bounded in the text, because an unbounded version broke a trial**: told only that a river "adds +1 commerce", an agent moved the capital one tile onto a river and onto its own wheat resource, paying a turn and the wheat for it. `CvPlot::calculateYield` floors a city tile at `iMinCity` 2/1/1, which absorbs that commerce entirely — so on the tile a city *stands* on, a river is worth exactly what a lake is. The legend and the site report both say so now, and the next trial reversed the ranking itself, calling it "a ranking I'd have got wrong." Flood plains are deliberately *not* a fresh-water source — `CIV4FeatureInfos.xml` gives them `bRequiresRiver=1` and `bAddsFreshWater=0`, so they sit on a river rather than supplying water. And river is not a subset of fresh water: a river crossing a **peak** reports `river=true, freshWater=false`, because a peak can never be farmed or settled, so treating river as "fresh, but stronger" would mis-glyph it. The cross table splits the same facts into two columns — `water` (`-`/`fresh`/`river`/`river+`) and `coast` (`-`/`sea`) — because farms-and-health and buildings-and-boats are different questions, and `sea` rather than `yes` so a row reads as a sentence without its header. All of this is explanatory: a river's +1 commerce (`RiverYieldChange` `0/0/1` on every land terrain) is already inside the exported yield, so the column tells you *why* a tile reads `2/0/1` and never changes the number.

**Yields that already include an improvement are marked `+`.** `map.tiles.yields` is the *displayed* yield, so a farmed tile reports the farmed number — wheat at (76,35) reads 2/1/1 at turn 0 and 5/1/1 at turn 34 once Lisbon farms it. Comparing two candidate sites then compares improved tiles inside your borders against raw tiles outside them, which **flatters whichever site overlaps a city you already own** — i.e. the site that costs you the most. Base yield is not recoverable from the export, so the honest fix is to mark the affected tiles rather than pretend the improvement can be undone; re-deriving base yield would mean reimplementing the engine's yield rules in the harness and getting them subtly wrong. Goody huts and city ruins are excluded (they sit in the `improvement` field but are not development), and so are roads — `CIV4RouteInfos.xml` gives `ROUTE_ROAD` and `ROUTE_RAILROAD` no `<Yields>` block at all, so a roaded tile's displayed yield *is* its raw yield. An agent trial confirmed the marker changes rankings: without it, it would have ranked a 6-tile-overlap site first on the strength of a wheat tile its own capital had farmed.

**The counts separate new land from land you already own.** Raw cross counts credit a site with tiles inside your existing cities' radii, which inflates exactly the sites that gain you least. At turn 34 two real candidates read 13 vs 12 workable land — near-identical — while the land actually *new* to the empire is 7 vs 11, and resources 2 vs 3. So when a cross overlaps, the block adds a second line reporting land / water / resources excluding the overlap. Same discipline as removing the yield `TOTAL`: the numbers stay descriptive, and the one that was quietly answering the wrong question gets its counterpart beside it rather than a caveat below it.

**A non-coastal site gets a note under the counts, not a column.** The temptation is to split the water count into coastal/non-coastal, but "water is wasted for a landlocked city" is false: `CvCity::canWork` gates water on `CvTeam::isWaterWork()`, which `TECH_FISHING` sets **team-wide**, not on the city being coastal. A landlocked city works its water tiles normally. What it actually loses is the Harbour and Lighthouse (both `bWater`, coastal-only), work boats — so seafood in the cross is unimprovable — plus naval production and overseas trade routes. A column named "wasted water" would have taught a false rule; the note states the real one and leaves the trade open.

**The site report flags a site one tile off the coast, and only then.** Radius 1, because beyond one step you are choosing a different site rather than nudging this one — and because a general nearest-X search is the first step toward the query language this folder refuses to grow. It reports and does not judge: one off the coast is often an accident but sometimes deliberate (fresh water, a resource, a chokepoint), so the line states the fact and hands the trade back.

**`settle` shows no fog, deliberately.** What constrains city placement is ownership and existing cities, not whether you happen to be looking. It is also the only view that draws settlers — the settler is the actor for that decision and where it stands is how far it has to walk.

**`worker` stops short of the tech tree.** The bonus → build → tech chain lives in the game's XML; walking it is the rules-lookup tool's job (below), and doing it here would make the tool depend on a Civ IV install. It names the XML files instead.

**What it hardcodes, and why that is bounded.** The founding rules — `MIN_CITY_RANGE`, which terrains and features can hold a city, the foreign-ownership block — are transcribed from `CvPlayer::canFound` and the game's XML **at development time**, so nothing is read from an install at runtime. One documented over-report: the engine only counts a nearby city on the *same landmass*, and no area id is exported, so a city two tiles away across water is marked blocked when founding is really legal. It never under-reports.

**How this was tested, and what the trials changed.** Fourteen agent trials, each given the same two turns of the baseline run — turn 0 (found the capital) and turn 34 (place the second city) — with the state JSON withheld so only the renders could carry the decision. Turn 0 came back correct in every trial but one - and that one is instructive, see the river note above. Turn 34 landed on or adjacent to the tile the human actually settled once the agent could crop with `--around`, and wandered when it could not.

Nearly every decision below is a trial finding rather than a prediction, which is why they are recorded with their evidence:

- Tables dropped relief and lake-ness, so a **peak printed as grassland yielding 0/0/0** — one tool contradicting itself between grid and table.
- **Coastal, overlap and settler-distance were being derived by hand** — coastal seven times in one session, because two near-identical candidate tiles differed only in it.
- The **improved-yield `+`** exists because a trial was about to rank a 6-tile-overlap site first on the strength of a wheat tile its own capital had farmed.
- **Horizontal indexing** was the persistent failure: trials repeatedly described a tile as its left neighbour. Cell separators, `||` grouping and repeated headers each helped and none fixed it; **cropping did**. The tool's advice to reach for `--around` is the conclusion of that, not a preference.

Two things trials asked for and did not get. **Overlap drawn on the `settle` grid**: a city works pop+1 tiles, so "6 tiles shared" describes contention that will not exist for 30+ turns — it is reported where it matters and would be over-weighted as the most prominent thing in the view. **Which city triggers an `x`**: `x` means "cannot found", and the cause does not change which alternative you pick.

**Why the cross reports counts and not a yield total.** It used to print `TOTAL: 27 food / 19 prod / 13 commerce`. That number was removed, not reformatted, because it ranked sites and ranked them wrongly. Coast is `1/0/2` forever and already at its ceiling; grass-jungle reads `1/0/0` today and `2/0/0` once a worker clears it — so summing *current* yields rewards finished tiles and punishes improvable ones. On the two real candidates at turn 34 it called the coast-heavy site the stronger one while quietly counting six tiles already inside Lisbon's radius as an asset. And a sum cannot see the thing that actually decides an early site: a city works pop+1 tiles, so one or two great tiles and a handful of good ones is enough, and 21 mediocre tiles is not better.

What replaced it is a count of what is *there* — workable land, workable water, unworkable, never revealed, overlapping your cities, carrying a resource. A count says how many chances the site gives you; the table above says how good they are; the reader weighs them against its own strategic horizon, which is exactly the judgement a tool must not make. **Unworkable means peaks only.** Deep ocean reading `0/0/0` is the engine quirk documented in the schema, and jungle reading `0/1/0` is a worker's to-do item — counting either as unworkable would smuggle the same bias back in through the counts.

**Legends carry decode tables and traps, not rationale.** Every legend line costs on every call, and the grid has to stay much cheaper than the JSON it saves you reading. Why a glyph is what it is belongs here and in the code comments — both read once. What belongs in a render is the decode table plus any trap that would cause a *wrong action* if missed.

**A region straddling the map's x seam now says so in words, instead of printing a range that looks backwards.** `axis_window` already computed the wrapped window correctly (walking east from the crop point, past x=83, back to x=0); only the *description* string was wrong, joining the two halves with a bare `xs[0]-xs[-1]` — a crop near the seam printed `x 80-4`, indistinguishable from a typo. 5 of 10 trials misread it. The fix names the edge in words (`x 80-83 then 0-3 (wraps past the east edge)`) rather than leaving the reader to infer which edge and combine two ranges themselves. x-only: `wrapY` is always false on the standard Civ4 cylinder map, so y never takes this path.

**`--site-only` (requires `--around`) skips the grid and prints just the site report.** The report was already there in `extra_sections()`; what was missing was a way to get it *alone*. Four trials found `--radius 1` as a workaround — it still draws a 3x3 grid, just a small one — and one piped output through `sed`. Implemented as an early return in `render()` once the shared preamble is built, reusing the same `extra_sections()` loop the normal path ends with rather than duplicating it.

**`yields`/`worker` flag a city `NOT GROWING` on a specific, checkable condition: `foodPerTurn <= 0` and the current build is not a Settler or Worker.** The naive version checked `productionFromFood == 0` instead, reasoning that a food-fed build shows food going into it — wrong, because a Settler/Worker can show `productionFromFood == 0` on an all-hammer turn (food banked earlier in the build) and still be exactly the deliberate, not-stuck case. Checking the unit type sidesteps the turn-by-turn funding split entirely. Not the whole engine gate — a Police State civic makes military units food-fed too — but the only case that recurs in scope, so `FOOD_COST_UNITS` stays a two-item constant rather than a general `bFood` lookup. States the fact and stops; it does not diagnose *why* the city is stuck (terrain, borders, happiness), matching this tool's present-don't-decide line.

</details>

### `run_history.py` — the run history

```
python harness/run_history.py <run-folder> [--view timeline|intel|lost] [--from N] [--to M] [--as-of N]
```

Takes a **run folder** of `turn_*.json` files — the whole game, not one turn. Three views: `timeline` (what changed, turn by turn), `intel` (per-rival dossier) and `lost` (own units that disappeared). Usage is in `AGENT_GUIDE.md`; the reasoning is below.

<details>
<summary><b>Design notes</b> — why it is cut this way</summary>

**`intel` splits each rival into two sections because they answer different questions and go stale at different rates.** `RECENT SIGHTINGS` is positional and perishable — where something was, most recent first, with the age in turns. `EVER FIELDED` is a permanent capability record: a unit type seen once is one they can build, and that stays true forever. The turn a type was **first** seen leads each line, since that is the fact that dates their tech. The two use cases that drove the split are not walking a vulnerable unit into a hostile, and reading a rival's tech level off what they have fielded.

**`intel` ignores `--from`/`--to` on purpose** and says so on stderr: a dossier truncated at turn M drops the earliest sighting of a unit type, which is precisely the fact that proves a capability. Clamping the *run* is a different thing and is what `--as-of` is for.

**Barbarians and animals are listed separately, and that split is load-bearing.** A Roman Archer implies Archery (`CIV4UnitInfos.xml` gives `UNIT_ARCHER` a `PrereqTech` of `TECH_ARCHERY`); a panther implies nothing about anyone. Both arrive through `foreignUnits` under the barbarian player id, so a single list would invite reading animal sightings as evidence about a civ. **They get full positions**, which they did not at first: the split was right and the barbarian half was under-built, printing a bare turn count. A trial called it "the section with no coordinates is the section I most needed coordinates from" — correctly, since this early the animals *are* the military threat, and it reconstructed the lion cluster at (71,33–34) by hand.

**The five changes after the first round of trials**, all from what agents did with the output rather than from review:

- **A settler consumed founding a city is no longer `LOST`.** Two trials read `LOST UNIT_SETTLER` as a casualty; one "nearly built an advisory around a second casualty that never happened". The pairing is an inference — the export never records which settler founded what — but safe at one settler and one city, and refused rather than guessed when either count is higher. It deliberately does **not** match on position: the settler moves and founds in the same turn, so its last exported position is a tile or more from the city (Oporto at (78,37), settler last at (77,36)), and a positional match would fail on the case it exists for.
- **`--as-of N` clamps the whole run** by discarding later files at load — the only version that cannot leak, since nothing downstream can reach a state never loaded. Three trials hit the footgun it fixes: a question set at t34 against a run reaching t40, with `intel`'s header asserting t40 was now. `--from`/`--to` remain `timeline` output scoping, which is a different thing.
- **Garrison counts** — three trials hand-joined `units` against `cities` by coordinate, one calling it the most important fact in its answer.
- **Distance from your nearest city.** Every trial computed Chebyshev by hand and one noted it could have got the `wrapX` term silently wrong. Nearest rather than per-city: one number is scannable, N numbers grow with the empire and mostly repeat.
- **The compass finding went to the guide, not the tool** — no output change can fix narration when the coordinates were already right.

**The garrison section counts and refuses to judge.** Whether an empty city is in danger depends on what can reach it, and **none of that is computable from the export** — no landmass id, so "can a land unit walk here" is unanswerable, the same gap that makes `settle` over-report founding legality across water. Printing "UNDEFENDED" would assert a threat model the tool cannot evaluate, and on a city reachable only by sea it would simply be wrong. So it reports who stands where and points at `--view military`. Same present-don't-decide line as refusing to rank sites, in a place where the wrong call looks helpful.

**Distance was Chebyshev, always labelled a lower bound**, ignoring terrain and borders; anything better is the pathfinding this folder declines to build. `render_map.py`'s site report said "a LOWER BOUND on turns, terrain costs more" — two tools disagreeing on what a distance means would be worse than neither printing one.

**That consistency argument was then broken by the tool that made it, and is now repaired.** `run_history` gained a land figure while the site report kept Chebyshev alone, so the two tools disagreed about the same map — exactly the failure the paragraph above warns against. `State.land_distance` gives the site report the same measure, and `test_land_distance_matches_run_history` asserts both implementations return the same number, so the two cannot drift apart again silently. The settler-to-site line was the one that mattered: it is the number an agent acts on before committing a settler, and an agent trial found a route whose straight-line figure implied open ground while the real walk crossed a one-tile isthmus.

**When the walk differs from the straight line, the walk leads.** Both figures were already printed side by side, straight line first, and two independent trials reported that the leading number is the one the eye takes — one saying it "still caught me on first read" *despite its instructions warning about exactly this*. Measured on the baseline map at t34: 62 of 135 walkable tiles diverge, and the worst reads 4 straight against 17 on foot, so the misleading ordering was the common case rather than a corner. Same lesson as the compass — when a caveat does not stick, move the layout instead of adding words.

**Then a second round of trials showed the label was not enough, so land distance was added beside it.** Two agents independently found that a lion sitting 6 tiles from Lisbon is a **14-step walk** — a bay forces the route right around — and both called the bare Chebyshev figure the most misleading number they were given: *"6 tiles is an emergency, 14 tiles is a non-issue."* Four of five trials wrote their own flood fill over `map.tiles` to recover it, one writing the same BFS three times, which is this repo's stated signal for a missing tool. So `intel` now prints the land walk whenever it differs, and says outright when there is no land route at all. **It is still not pathfinding**: no terrain costs, no unit rules, no routing through fog — a plain BFS over revealed non-water, non-peak tiles, which is what the agents were writing anyway. Fog is the honest limit and is stated rather than papered over: the figure is the best *known* route, so an unrevealed shortcut can only make it shorter.

This also corrected something the guide had asserted. It told agents reachability was "unanswerable from the export" because no landmass id is exported — and four of five answered it anyway in about ten lines. What is genuinely unanswerable is connectivity *through unrevealed land*, which is a much weaker claim. Teaching a limitation that is not real is its own kind of wrong.

**The compass is drawn on the output because prose demonstrably does not fix it.** Ten trials across two rounds read coordinates correctly and then narrated north and south inverted — **all ten**, including five given the orientation in bold, first in their instructions, with a worked example and a warning naming this exact failure. East/west was never once wrong. The asymmetry is the diagnosis: `x` behaves as expected and `y` does not, so the sign gets normalised away silently while every coordinate stays right, which is why no amount of correct output catches it. The fix is therefore to remove the derivation: the grid is bracketed by `N ^ NORTH` / `S v SOUTH` rules on the edges they name, and `run_history` prints a bearing (`16 NNW of Lisbon`) so direction is read rather than computed. The compass survives `--brief`, because it is orientation, not legend.

**The compass reduced the failure; it didn't eliminate it, so the export itself now inverts the coordinate space** (`meta.schemaVersion: 2` — see root `CLAUDE.md`): `(0,0)` is northwest, `y` increases south. Every coordinate cited above and in `samples/README.md` reflects the migrated data.

**`lost` is scoped to an event, not to an object, and that is what keeps it from becoming a query tool.** The ask was `--unit <id>`; what got built answers the question that is actually asked. "What happened to my unit" came up in both trial rounds, cost three ad-hoc scripts each time, and a unit dying is one of the most advice-triggering events in the early game — but a general per-id browser is one step from the `--filter`/`--sort` language this folder refuses, whereas "units that disappeared" cannot grow into one. It gives the track, the damage history, the final turn's reveal diff and what was in sight, then stops. **It deliberately does not infer the death tile** from the reveal pattern, though a trial did that well twice: weighing which tile explains a reveal shape is judgement, and a heuristic in here would get it wrong quietly. The view hands over the evidence and states the rule (radius 1 flat, radius 2 on a hill) instead.

**The loss line now says `last exported at`, and carries distance and bearing.** Two trials read the old `last at (69,33)` as the death tile; it is the last position ever *exported*, from the previous turn's snapshot, and a unit moves during the turn it dies. The same line also had no distance while every rival sighting three sections above had one — backwards, given that "how far away was this" decides the response, and it was the one number a trial wrote a BFS to recover.

**Non-combat occupants are flagged.** Two trials read `Lisbon (75,36) SETTLER` as a garrison before registering that a settler has combat 0, so the count was quietly overstating the position. The unit list is transcribed at development time like `render_map.py`'s founding rules, and is deliberately short — a unit missing from it is simply unflagged, which is the safe direction, since the tool never claims something *can* fight.

**Posture sits on the occupant line, because a garrison count was never the whole fact.** Increment ⑨ exported `activity` and `fortifyTurns` and no tool read either, so the guide had to send the agent to raw JSON for something belonging on a line it was already reading: a Warrior at `fortifyTurns: 5` carries **+25% defence** over one that walked in this turn. Both fields are read because neither implies the other (no `ACTIVITY_FORTIFY` — see REFERENCES.md "Unit orders"); reading the activity alone would print "sleeping" over a dug-in defender. The percentage is the one number this tool computes that the engine also computes — `fortifyTurns × 5` capped at 25, transcribed rather than read from XML, since `run_history.py` never opens the install. An unrecognised activity falls back to its own name, so a value added to the schema later is printed rather than silently dropped.

**The objectives staleness line fires with no flag, and that is the entire point of it.** The trial brief asks for objectives restated every 10 turns; a trial wrote them at t0, updated to t10, then went silent to t36 — through first contact with two civs, a completed Settler and a unit loss. The queued `--objectives PATH` was dropped rather than built: it replaces "remember to check the file" with "remember to pass a flag that checks the file", which fails the same way one indirection deeper. There is deliberately no override.

**That was possible only because the roadmap's stated blocker was measurably false.** It held that `state/` is a junction into the repo's own `state/<game>/`, so walking up from the run folder resolves through the link and reports "never written" on every real trial — silently, looking exactly like genuine drift. But `os.path.abspath` collapses the `..` **textually, before touching the filesystem**, so it never follows the link. Verified against a generated junction for every path spelling the advisor might type, and `test_objectives_lookup_does_not_follow_a_junction` holds it. Do not "fix" this to `realpath` — that is the version the roadmap described, and it fails in the silent direction.

**The age is inferred from mtimes, so it must refuse when it cannot tell.** `objectives.md` carries no turn number, so the turn it was written on is the newest turn file older than it — true in live play, false on a fresh clone or reloaded save (git restamps at checkout; a reload rewrites one turn in place — see `turn_files`). The ordering check is **strictly** ascending for that reason: an earlier version used `<=`, which equal timestamps satisfy, so a freshly-cloned run reported the *latest* turn at "0 turns ago" for arbitrarily stale objectives — wrong in the worst direction, since it claims freshly-restated. Equal mtimes are the signature of the case the check exists to catch, so they have to fail it.

**Rival territory needed its own branch, not a wider diff.** Borders of a civ you have never met arrive **already owned on the turn the tile is first revealed**, so there is no previous value and an owner-*change* diff never fires. The Greek border at (66,32–34) on t35–36 — the first hard evidence of a Greek city's location in the whole sample, and the basis for a trial's strongest inference — produced zero lines. It now reports the tiles and notes that a border implies a city within about two tiles, possibly beyond the revealed edge. **Small reveals also list their coordinates** (up to `MAX_REVEALED_LISTED`): a trial reconstructed where a unit died from exactly those five tiles, having written Python to recover what the tool had reduced to a count. Above the cap a reveal is a scouting sweep rather than evidence, and the coordinates would bury the block.


**Continuity is a constructor assert, not a view.** Save-scumming into a different branch is out of scope: reloading an older save rewrites that turn and leaves later files from the abandoned timeline behind, producing a folder that looks continuous but is not. Rather than report and work around it, `Run.__init__` raises and `main()` exits 2. It was briefly designed as a third `check` view; that collapsed once branch support was ruled out, because nobody asks "is this run sound?" as a question when the answer is enforced on every call. **Fatal:** setup-signature disagreement, duplicate or backwards turn numbers, techs unlearned, revealed tiles forgotten, a city id reused under a new name. **Not fatal:** a turn gap — a failed export is logged and skipped rather than crashing the game, so gaps are legal. They are reported in the header *and* labelled on the block that spans them, since a diff across a two-turn gap covers two turns of change and would otherwise read as one.

**The fog distinction is the whole tool, and a position-keyed diff without it is mostly noise.** Measured on the baseline run: at t35–t40 two rival scouts are continuously observed *while moving*, so a diff keyed on `(owner, type, x, y)` reports them vanishing and reappearing every single turn — six turns of "gone!" about units that never left sight. Classifying each departure against the *next* turn's `visibleNow` is what separates that from the real case, and the same run has both on one turn: at t27 Rome's garrison reads `lost sight` (its tile fogged) while a lion two tiles away reads `left or died` (its tile stayed visible).

**Own units and rivals' units need different machinery, because only ours have ids.** Our `units` and `cities` carry stable engine ids, so their diff is exact — the warrior lost at t38 is an unambiguous id disappearance, and the settler consumed into Lisbon at t1 is visible as id 8192 leaving `units` as a city of the same id appears. `foreignUnits` has no id at all, so nothing there can be tracked, only observed. Every asymmetry in the output follows from that one fact.

**`intel` reports observations and never concludes.** It says a Roman Archer was seen on t26; it does not say Rome has Archery. That join belongs to the rules-lookup tool plus the agent's judgement — so the section names `CIV4UnitInfos.xml` and stops, the same way `render_map.py`'s `worker` view names the XML rather than walking the tech tree itself. This is not pedantry about where a lookup lives: writing these notes, I asserted from memory that an Archer implies *Bronze Working*, which is the Axeman's prerequisite. The XML says `TECH_ARCHERY`. A tool that printed a confident tech conclusion would have printed that same wrong one.

**Foreign city population needed no staleness treatment, contrary to first appearances.** Rome's tile is visible only at t26 and fogged for the remaining fourteen turns, yet its population moves 4 → 5 → 3. That is not stale data: the schema exports `foreignCities` fields **live**, because the engine paints the real nameplate through fog with no visibility gate. So the latest value genuinely is current, and only the turn it was recorded is printed, for provenance. Marking these "possibly stale" would have taught a false rule about the export.

**Stacks collapse to one line with a count.** Two Roman archers on one tile at t26 printed as two identical lines, which reads as a rendering fault rather than as the militarily relevant fact that it is a stack.

**Tile changes are tracked on five fields and terrain is deliberately not one.** `improvement`, `route`, `owner`, `bonus` and `feature` change meaningfully; terrain never changes, so a change would mean a broken run, which the continuity guard owns. `visibleNow` is excluded because it flips constantly by design — that is the fog, not the world moving. `bonus` appearing gets its own wording (`RESOURCE NOW VISIBLE`) because the resource was always there and a tech is what unhid it: in the baseline run `BONUS_HORSE` appears on two tiles the same turn Animal Husbandry completes, and both facts land in the same block, which is what makes the causation readable without joining two files by hand. The two `feature` changes in the run (jungle t29, forest t39) are the engine's feature-growth mechanic; the tool reports the observation and does not guess the cause.

**What was considered and not built.** An `own` view — your own empire's trajectory across the run — was dropped: that is four numbers per turn, and an agent reading five JSON files gets it unaided. The bar is where the agent is *unreliable*, and the expensive cases are the ones that span many files. Whether it is wanted is left to the agent trials to report rather than guessed at now.

**This tool makes none of the renderer's deferred requests cheaper.** Comparing several `--around` sites (still open — see `ROADMAP.md`) and movement cost are single-turn spatial concerns; nothing here touches them.

**Own cities lead `intel`'s output; barbarians come next, rivals last.** All three answer "is anything about to hurt me", just at different urgency: your own empire first, the threat that needs no tech implication and is the main early danger second, per-rival capability dossiers — lower-urgency reading — last. Previously the garrison block was printed last, after every rival dossier, and 7 of 10 trials lost track of it there, one saying it nearly scrolled past the most important line in the output. Same fix shape as the compass and the walk-vs-straight-line ordering above: when a caveat or a fact does not stick, move the layout rather than add words.

**Production history is reported on both views, because what a city builds is a decision the export makes invisible.** 4 of 6 trials went to raw JSON for it after `intel` told them a city was empty, and the run's sharpest fact needed a hand-written loop over five files: Lisbon abandons a Worker at 27/60 on t38 and resumes it at 39/60 on t40. `timeline` gains a line per change of `producing`; `intel`'s garrison block gains the current build and an ETA beside the defender count. Two halves of one fact — a city that is empty *and* building a Settler is a different situation from either alone. The food share of the rate is repeated here as the growth cost, which `Findings` records a trial reading past in `rules.py city`: placement, not volume, per the compass and garrison-block reorders above.

**Completion is inferred from the item arriving, never from the production total falling.** There is no "completed" flag, and the first implementation read a falling `production` as one — wrong in a way the sample proves, since dropping a Worker at 27/60 for a Warrior at 2/15 falls exactly as finishing it would. So `COMPLETED` requires the thing to appear: a unit in that turn's gains, or a building in `cities[].buildings`. Everything else is `SWITCHED`. This works because `producing` and `buildings` are both `BUILDING_` form, so our own wonders match like any building; the top-level `wonders` is deliberately not consulted, being `BUILDINGCLASS_`-keyed (not interconvertible — see `CLAUDE.md`) and global, so joining it would credit our city with a rival's build. A **process** is the one gap, and cannot be otherwise: it never completes. The failure mode avoided is the repo's recurring one — a plausible, self-consistent, wrong line nothing else in the output can contradict.

**A completion that empties the queue needed its own wording**, being the commonest production event there is: the engine exports `producing: null` on the turn an item lands, with the next choice made the turn after, so the naive reading splits one normal build into "stopped X" and "started Y" — two non-events. Both branches take the same arrival evidence.

**`turns_to_complete` reimplements `ceil((needed - current) / rate)` rather than importing it from `rules.py`** — arithmetic over three exported fields is not a rules lookup, and importing would couple this module to a 3300-line one with several queued items about to churn it (`ROADMAP.md` left the call open; this is it). It returns `None`, and prints no estimate, for an empty queue, a process (`productionNeeded` is `null` for both) and a city producing nothing per turn, where "never" is the honest answer and any integer would be a lie. The estimate is at today's rate and says so: `productionPerTurn` carries one-off overflow after a completion and folds food in while a food-fed build is queued.

**`timeline` flags a gold swing that does not match the previous turn's rate, and only that.** `player.gold`/`goldPerTurn` were already exported and unused here. The motivating case: a goody hut added 60 gold with nothing else in the export accounting for it, and the agent only found it because the player mentioned it out loud. `goldPerTurn` describes *this* turn's rate, so comparing a turn's actual delta against the *previous* turn's rate is what catches a jump the ordinary rate cannot explain — comparing against the same turn's rate would compare the number to itself. It is deliberately silent on ordinary turns: `timeline` already skips turns where nothing changed, and gold changing by exactly its own rate is not a change worth a line.

</details>

### `rules.py` — the rules lookup

```
python harness/rules.py unit|tech|building|promotion|city|handicap|goody|improvement [TYPE] <state.json> [--show-known] [--depth N]
```

Reverse and transitive lookups against the game's XML, priced for the game in the state file. Usage is in `AGENT_GUIDE.md`; the reasoning is below.

<details>
<summary><b>Design notes</b> — why it is scoped this way</summary>

**The three traps are measured, not assumed.** Checked against the real install before writing anything: `find -iname CIV4UnitInfos.xml` returns **18 hits** with the vanilla `./Assets/XML/...` first and the BTS copy second — the other sixteen are mod copies, and Final Frontier's "units" are spaceships. `PrereqTech` sits at **line 90** of the `UNIT_AXEMAN` block, not the ~30 the roadmap estimated, so `grep -A6` is not close. And the handicap fields genuinely differ where it matters: the baseline sample is **Emperor**, where barbarians start at turn 20 with `iFreeWinsVsBarbs` 0, against turn 35 and 2 free wins on Noble. Every copy of every file parses cleanly, so a wrong pick is silent.

**"Vanilla is the wrong answer" was itself wrong, and an agent trial proved it.** The first version resolved BTS-only and asserted the path contained the BTS segment. But an expansion only ships the files it *changes* — measured on the install, `Terrain/CIV4BonusInfos.xml` (every resource's `TechReveal`) and `GameInfo/CIV4GoodyInfo.xml` exist **only** in the base tree, because BTS never altered them. A trial needed `TechReveal`, followed the BTS-only advice this repo had written into `AGENT_GUIDE.md`, found nothing, and fell back to grepping. The rule is now BTS-first, vanilla-fallback, which is how the engine itself resolves; the `Mods/` copies stay excluded, since those are the genuinely wrong ones. `read_xml` returns which tree answered, and a file in neither is an error rather than a guess.

**Path resolution asserts rather than searches.** `resolve_xml_root` composes both roots from `config.local.json`; a missing config is fatal rather than defaulted. Searching is what finds the mod copies. This is the first Python consumer of `config.local.json` in the repo.

**Regex, not `ElementTree`, for one specific reason: line numbers.** A block prints as `file:line` because a bare path leaves the agent grepping — which is the trap. `ElementTree` discards source positions. The files are also machine-generated and flat, which is the case where regex is safe.

**A citation is for what the view did NOT print, so a view that exhausts its source cites nothing.** The point of `file:line` is the guide's own escape hatch — when the tool doesn't cover something, go read the install — and that is worth a line only when something is left to find. `UnitInfo` carries 130 distinct tags and `HandicapInfo` 67, so `unit` and `handicap` land a reader somewhere with more to give. `CIV4GoodyInfo.xml` carries 19, and `goody` already renders every one that bears on a decision, so it is deliberately uncited even though it supplies half that view's data. Citing it would only offer a trip that ends where it started.

**Tech cost is computed, and the formula is verified against the engine's own numbers.** `cost = base × speed% × world% × handicap%`, **truncating at each step**. Verified exact on all four techs the baseline run reports a cost for (Agriculture 60→93, Animal Husbandry 100→156, The Wheel 60→93, Writing 120→187). `test_cost_matches_every_sample_turn` re-checks the formula against `player.research.cost` on *every* turn of *every* sample, so a future capture at a different speed or world size fails the test rather than disagreeing silently. Stepwise-versus-single-pass truncation agrees on most values and diverges on some, which is exactly how a wrong version survives a small test — the unit test picks a value where they differ (12 vs 13).

The **met-civs-know-tech discount is deliberately not in the formula**: it applies to the research *rate*, not the cost, and is already inside `player.beakersPerTurn`. That was checked rather than assumed, and it means `cost ÷ beakersPerTurn` is a legitimate estimate because both sides are already correct.

**`--state` is mandatory, not optional.** Without it every cost is 1.0–4.5× wrong, and an agent will compare a base cost against `beakersPerTurn` anyway. Making the good path optional means the bad path gets used. It costs the agent nothing — the file is already open in every question it asks — and it gives the tool a continuous cross-check, since every invocation prices against a real setup. The cost: this no longer answers a pure rules question without a game in hand, which is correct for advising tooling and consistent with this folder's "take a state-file path" constraint.

**The closure is walked in full, because depth was the wrong worry.** Measured before choosing: the whole tree is 92 techs and the largest full closure is 14, with early-game targets at 1–7. Civ4's ancient tree is wide and shallow. So there is no cutoff to defend, and a *truncated* closure is precisely the confident-but-incomplete answer this tool exists to prevent. `--depth` truncates the printed tree only; totals always cover the full walk, since a partial total is a wrong number while a partial tree is visibly partial.

**Prerequisites are an AND/OR DAG, and flattening it is the failure mode.** 83 of 92 techs use `OrPreReqs`. Monarchy needs Priesthood **or** Monotheism; a naive union says it needs both, which would report Monotheism — a mid-game tech nobody routes through — as a requirement. The tree prints `ANY ONE OF:` for or-lists and leaves and-lists unlabelled, and a test asserts an and-list is never rendered as a choice.

**The union total is described as coverage, never as the cost.** Summing the closure across both or-branches gives a number nobody ever pays: 762 beakers for Monarchy against ~451 for the route actually walked. Printing it beside the per-route figures would invite reading it as "the cost", so the wording says it covers both routes and that you pay one.

**Route costs are printed and never ranked** — XML order, no "cheapest" label, no sort. This is the closest the tool comes to the present/decide line, and route totals are what make `--state` worth having, since a shared prereq you already own drops out of both branches and can narrow the gap. A test asserts the output contains no ranking vocabulary. If a trial shows an agent treating the lower number as a recommendation, this is the first thing to cut.

**Known prerequisites are hidden by default with a count, not silently.** The tree then shows only what you would still have to research, which is the actual question; `--show-known` restores them.

**Three bugs found during development, all of the same kind.** Recorded because they are the argument for the tool existing:

- A hand-grep with `-B95` put `UNIT_MAYA_HOLKAN` in the Axeman's sibling list. It is a **Spearman replacement needing `TECH_HUNTING`** — the window had crossed into a neighbouring block. The parser was right and the grep was wrong.
- The mockup asserted the Axeman is **+100% vs melee**. The XML says `iUnitCombatMod` **50**.
- A worked example asserted a **cycle** between Monarchy and Monotheism. There is none — Monotheism needs Masonry and Polytheism. The cycle guard stays because a recursive walk without one turns a data change into a hang, but it has never fired on real data.
- A draft read the Pyramid's `<iCommerce>6</iCommerce>` as **gold, plus "+1000 culture on completion"**. It is +6 *culture* per turn. Building fields are **positional arrays with no labels** — a Library's `<CommerceModifiers>` means +25% science only because index 1 is `COMMERCE_RESEARCH` — so the order is now read from `CIV4CommerceInfo.xml` rather than remembered.
- The tool itself printed `cost 35 hammers (base XML; scales with game speed)` — naming a multiplier it never applied. A trial quoted the raw number and said outright it was not confident it matched the city screen. It was right: `CIV4GameSpeedInfo` has `iTrainPercent`, but `CIV4HandicapInfo` has only `iAITrainPercent`, so **difficulty does not change what a building or unit costs the player** — unlike research.

The first draft of the closure also **stopped one level down** while printing the words "full walk" — it added a node then recursed on it and hit the already-seen guard immediately, reporting 2 prerequisites for Monarchy instead of 7. Caught by the tree and the totals disagreeing on screen, which is an argument for printing both.

**Unit siblings report their unit class rather than being called replacements.** Everything gated on the same tech is listed, because seeing a `UNIT_GREEK_PHALANX` and seeing a `UNIT_AXEMAN` are the same tech conclusion — the join `intel` deliberately refuses to make. Same class means one replaces the other; a different class means the tech unlocks both. Asserting "replacement" is what the Holkan error looked like.

**Handicap is a forward lookup and is included anyway.** The roadmap said reverse-and-transitive only, but its stated *reason* was that forward lookups the agent greps fine — and two trials changing conclusions on these fields is direct evidence it does not. Following the reason rather than the letter. The fields are also non-obvious in a way that punishes a quick grep: `iAnimalBonus` is **negative** and applies *to the animal*, so `-40` reads as "animals are stronger" unless the sign is explained, which the output does.

**An explicit handicap that is not the game's own is flagged.** Comparing difficulties is legitimate, but the header then shows two handicaps and the one being reported is not in effect.

**No turn-window notes in the output.** An early draft observed that turn 35 falls inside the advising window; that was cut. The cutoff is prompt guidance and has deliberately never been in code — same reason it is not in the mod — and the player may run this at any turn.

**`UNLOCKS` resolves every category, because the narrow version taught agents to guess.** The first version resolved only units and printed `buildings not reported - grep CIV4BuildingInfos.xml`. Two trials filled the gap **from memory** — the one thing `AGENT_GUIDE.md` rule 5 forbids — and they were not being careless: a tech with no unit rendered as `units (none)` and nothing else, reading as "this tech does nothing". `TECH_BRONZE_WORKING` printed four units, three of them other civs' uniques the player can never build, while its actual value in that position was copper reveal, forest chopping and Slavery. An authoritative-looking block with a load-bearing omission is worse than no block. It now reverse-indexes buildings, civics, projects, improvements, worker actions, resource reveals and resource usability, plus the tech block's own ability flags.

**Worker actions needed the nested prerequisites, not the top-level one.** `BUILD_MINE` gates on `TECH_MINING`, but inside `<FeatureStructs>` each feature carries its **own** `PrereqTech`: removing `FEATURE_FOREST` needs `TECH_BRONZE_WORKING` and yields 30 hammers. So "Bronze Working lets you chop" is a nested fact, and a flat index over `PrereqTech` would instead credit Bronze Working with unlocking `BUILD_MINE` — wrong, Mining does that. The output collapses these **per feature rather than per build**: every improvement that can sit on forest carries an identical struct, so the raw list is twelve near-identical lines all saying one thing.

**Religion is printed as a race, in its own block.** The first team to the tech founds it and later arrivals get nothing, so listing `RELIGION_JUDAISM` under `UNLOCKS` would state a guarantee the game does not make. Whether someone has already founded it is not in the export, and the block says so.

**Tech ability flags are transcribed because nothing reverse-indexes them.** `bBridgeBuilding`, `bIrrigation`, `bWaterWork` and friends are effects on the tech block itself, with no row in any other file. `bTrade`/`bGoodyTech` are deliberately excluded — nearly every tech sets them, so printing them buries the meaningful ones.

**Turn estimates are in, having initially been refused.** The first version printed costs and told the agent to divide by `beakersPerTurn` itself. Three of six trials did exactly that by hand, one of them three times in a single session, and one said plainly it would rather the division happened in tested code. Refusing it never prevented the arithmetic — it just moved it somewhere unverified. It is arithmetic over two exported numbers, not a plan, and every figure carries the extrapolation caveat.

**Near-match suggestions exist because type keys are unguessable.** Unique units are civ-prefixed and inconsistently so: `UNIT_ROME_PRAETORIAN`, `UNIT_MAYA_HOLKAN`, `UNIT_NATIVE_AMERICA_DOG_SOLDIER`. An agent reasoning from the *display* name guesses `UNIT_PRAETORIAN`, and the original error message said "check spelling against the XML" — sending it to grep, the exact behaviour this tool replaces. The candidates are parsed and in memory at the point of failure, so suggesting them costs nothing.

**Resource prerequisites resolve to three states, and the tool used to answer only two of them.** It reported whether a resource was revealed and how many tiles carried it, then disclaimed the rest: *"also needs to be inside your borders, improved, and road-connected... Not checked here."* That was written believing connectivity was unknowable from the export. It is not — `player.bonuses.counts` is the engine's own connected-resource figure, and the schema describes it as "what the trade network actually delivers", so the tool held the answer while printing that it did not. Three of four agent trials hand-joined `map.tiles` against `player.bonuses` to recover it; one named the asymmetry exactly, that the negative case ("NOT YET REVEALED, so 0 visible is not evidence") was done well and the positive case not at all. Now: **CONNECTED** (buildable today, with where), **visible but not connected** (naming which of borders / improvement / road is missing, per tile), or **not revealed** (zero is evidence of nothing either way). The distinction decides whether a unit is available this turn or in twelve.

**What it deliberately does not do.** Corporations, espionage and great-person effects are out of scope for the current turn window. And it never suggests what to research. Promotions moved out of this list once the mod started exporting `units[].promotions` (schema increment 7, see `rules.py promotion`).

**The `unit` combat block was audited whole, because sampling it kept finding more.** It began as a one-field fix: `iAnimalCombat` was missing, so a trial hand-estimated a Scout's odds against a Lion and flagged the number as a guess. Checking three unrelated units on the way out (samurai, axeman, chariot) found four further readable, unprinted fields — and each subsequent question found another. The generalisable failure: **`parse_units`' field list had never been checked against the block it parses**, so whether a field was printed was uncorrelated with whether it mattered. All 207 distinct tags across the 123 `UnitInfo` blocks were then enumerated and classified rather than sampled, which is what closed it.

What that added, beyond the original animal bonus: **unit-class modifiers** (`<UnitClassAttackMods>`/`DefenseMods`), where a Chariot's +100% vs `UNITCLASS_AXEMAN` — its entire purpose — was printed nowhere because it lives in a different container from the `<UnitCombatMods>` already parsed; **`iCityAttack`**, whose absence meant the view showed the defending half of the assault matchup and hid the attacking half; **`iBombardRate`**, **`iCollateralDamage`** and **`iCombatLimit`**, which together are why a Catapult is worth building and why it cannot finish anything; **`<UnitCombatCollateralImmunes>`**, and **`bNoBadGoodies`**.

Four rules came out of it, each learned by getting one wrong first. **Check the container, not the field name** — flanking, free promotions and class mods are all nested `(target, value)` pairs, and a flat `<iFlankingStrength>` sweep reads as though the unit flanked everything. **A default is not a fact**: `iCombatLimit` is 100 on 83 units and 0 on 34, so printing it unconditionally puts a meaningless line on nearly every unit. **Fields are shared between mechanics** — `iCollateralDamageLimit`/`MaxUnits` are non-zero on 25 units that deal no collateral, because flanking reuses them, so the output gates on `iCollateralDamage` itself; gating on the limit reports a Knight as a siege unit. And **attack and defence keep separate wordings**, because a Chariot's +100% is a reason to attack while a Greek Phalanx's +100% vs chariots is a reason to sit still — collapsing them inverts the advice.

**`bNoBadGoodies` is the one that changes advice rather than describing a unit.** Only the Scout and the Explorer carry it, and it means they cannot draw a hostile goody-hut result on any difficulty. The trial that lost a Warrior to a hut lost it to a roll a Scout was immune to — so the useful answer to "should I pop this" is not only the odds but which unit to send, and the odds table alone never says so. Deliberately printed as the consequence ("never triggers a hostile result from a goody hut") rather than the field name.

**`goody` is a separate subcommand because `handicap` was answering its question wrongly, not incompletely.** The most expensive single finding of the Ramesses trial: a hut sat one tile from the scouting Warrior at t9, the agent ran `rules.py handicap`, read `iBarbarianCreationTurnsElapsed = 25` and told the player it was safe for another 16 turns. The hut produced a hostile warband that killed the player's only unit, leaving the capital undefended and unscouted. That field gates **map spawns** and nothing in the hut path — `CvPlayer::doGoody` never reads it — so the block was not merely silent on huts, it was actively misleading about them, with nothing in the output able to contradict it. Same shape as the `city`/`effective_known` bug: an authoritative-looking block whose omission is load-bearing. So the fix is three-sided rather than just the new subcommand — the field's description carries a `MAP-SPAWNED` qualifier, `handicap`'s OMITS redirects to `goody`, and the guide's rule-5 table gains a "never `rules.py handicap`" row, since each catches a reader at a different point.

**The flat percentage the ROADMAP specified is not the number the engine rolls, and finding that out was most of this item.** The item asked for the 20-entry table with the hostile rows visible — on Monarch, 5 of 20, "a flat 25% from turn 1". The counts check out exactly (a `needs_install` test pins all nine difficulties), but the draw does not: `CvPlayer::doGoody` **re-rolls** an ineligible outcome rather than skipping it, so blocked entries push weight onto the rows that remain, hostile included (mechanism and citations in REFERENCES.md). Since several outcomes are gated early, the trial's own turn 9 is really **31.2%, not 25%**. **The early game is when a hut is most likely to be hostile, not least** — the opposite of the intuition the spawn-timer field creates. Building this from the XML alone would have produced a plausible, defensible, wrong table: the failure the tool exists to prevent, one level up.

**The gates that block hostiles outright are temporary in a way that reads backwards.** `canReceiveGoody` refuses a hostile result when you have no cities, and at exactly one it refuses within `8 - getNumCities()` = 7 tiles of it. So the protection a player assumes grows with their empire in fact **ends the moment they found their second city**.

**The caller can supply what the remaining gates need, and originally was not asked to.** The first version took a unit *type* and listed three things as unknowable: the one-city radius, the unit's damage, and whether it could still promote. Two were not unknowable at all — they were **already in the state file the caller had to pass anyway** (`damage` is exported; a hut is any `map.tiles` entry with `improvement: IMPROVEMENT_GOODY_HUT`, the only `bGoody` one in either tree). What was missing was just *which* unit and *which* hut, so `--for-unit ID` and `--at X,Y` were added. **OMITS shrinks as they are supplied** — a line claiming ignorance of something just decided is the same authoritative-looking wrongness this subcommand exists to remove, inverted.

**What it will not assert is the other half of that.** `CANNOT` is reserved for gates decidable from the state file and the XML alone; anything else prints as a condition. Getting that line wrong once was instructive — a first draft printed `CANNOT` on the healing row whenever a unit *type* was given, but a healthy Warrior and a half-dead one are the same string, so it asserted something unseen and would have understated the hostile share by shrinking the eligible pool on a false premise. And it never prints "safe" or "unsafe" even fully specified, which a test enforces: supplying the unit and the hut makes the *percentage* exact, but whether 31% is worth the unit is judgement rather than lookup.

**The hut is a target tile and is validated as one, not trusted.** A unit standing on a hut has already popped it, so `--at` is never the unit's position — a caller passing that has made an error the tool can detect, and both it and a coordinate with no revealed hut are refused with the real ones listed. A typo would otherwise produce a confident distance to the wrong tile, the exact failure class this subcommand exists to remove. Revealed huts are listed whenever none is named, for the same reason the immunity is printed unprompted: an unadvertised flag is a flag nobody uses.

**This repo now holds two distance metrics on purpose, and the naming was the hazard.** The engine's `plotDistance` is `max + min/2`, not Chebyshev — 4 against 3 at (3,3), diverging on every diagonal (see REFERENCES.md). `render_map.py`'s `distance()` is Chebyshev and **correct for its own use**, since the city-minimum rule it serves really is a square box scan; but its docstring called it "the engine's plot distance", which was the wrong name for the right code and would have got it reused for the goody radius. Fixed there, implemented separately here — two functions both called "distance" is the trap, so each is now named for the engine function it actually is.

**`canAcquirePromotionAny()` stays in OMITS even fully specified.** `promotionsAvailable` counts what banked XP funds, so a positive proves the unit can promote — but zero proves nothing, the field being omitted at its default and a unit with no XP promoting fine once the goody grants some. The engine's own check is a sweep, not a stored value. Better to decide the turn half of the XP gate and name the rest than to let a plausible reading of an absent field settle it.

**The unit is a flag rather than the positional TYPE, and the immunity is stated whether or not one is given.** TYPE is the handicap here, matching `handicap`, so the unit needed somewhere else to live. Printing the immunity unprompted matters because the trial's failure was that *nobody knew to ask*: an answer available only to a reader who already suspects it would have changed nothing.

**The view was cut back to what a decision turns on, which is less than what is true.** It first printed the roll mechanics, every row's multiplicity beside its share, and the renormalised table in full — all accurate, none of it acted on, since the shares already encode the multiplicity and nine of ten renormalised rows moved under 1.5 points. **72 lines to 41**, mechanism moved to REFERENCES.md, leaving only figures that change a recommendation. The two pieces of mechanism that survived earn it by being counter-intuitive rather than merely true: the spawn-timer correction, which a trial acted on backwards, and the guaranteed barbarian floor, since `iBarbarianUnitProb` reads as "chance of trouble" and is really "how many extra". The raw shares still sum short of 100% and the gap is still named, because a table that silently fails to add up reads as a bug.

**`iBarbarianUnitProb` is how many *more*, never whether any at all.** Read naively, `GOODY_BARBARIANS_STRONG`'s 40% says "60% of the time nothing happens". Wrong: `receiveGoody` makes a second pass that ignores the probability entirely until `iMinBarbarians` is met, so 2 units land guaranteed and the 40% governs each further adjacent tile. Stated floor-first in the output for that reason.

**Holders and animal names are looked up from the parsed data, never hardcoded.** `UNIT_SCOUT` is the only unit with an animal bonus and there are exactly four `bAnimal` units, but both are facts about the current file rather than rules — a hardcoded name reads as an engine special case and goes quietly wrong under a mod, which is exactly what `MOD_WARNING` cannot cover.

**`TerrainImpassables`/`FeatureImpassables` are reported as-is, and some movement rules are simply absent.** "A chariot cannot cross jungle" is not in `CIV4UnitInfos.xml` — those fields are empty for `UNIT_CHARIOT`. Rather than infer, the output omits and says the SDK holds rules it does not report.

**`building` was added because the tool created its own dead end.** Once `tech` resolved buildings, `UNLOCKS` would tell you Pottery gives a Granary and then nothing could say what a Granary *is* — worse than the honest "grep it yourself" it replaced. The trial evidence was already there: the Barracks trial hand-derived `iCost` 50 from raw XML and then said outright it was not confident the number matched the city screen. Wonders come free, being the same file and the same block shape.

**What separates a wonder is not in the building's own block.** `iMaxGlobalInstances` 1 (one per world) and `iMaxPlayerInstances` 1 (national wonder) live in `CIV4BuildingClassInfos.xml`, and the join runs *backwards* through `<DefaultBuilding>` because a `BuildingInfo` does not name its class. That works for standard buildings and fails for unique replacements — the Incan Terrace is no class's default — so those report "class not resolved" rather than being silently called ordinary. The distinction leads the output because it changes the decision more than any effect: "50 hammers, build everywhere" and "500 hammers, one per world, possibly already lost" are different kinds of object.

**A world wonder is a race the export cannot see**, so it gets the same treatment as founding a religion: the fact is stated, and the tool says outright that rival production is invisible and losing converts hammers to gold. Silence about a competitor is not evidence there isn't one.

**The game's own strategy text is printed beside the parsed fields, because neither is complete alone.** The Pyramid's best-known effect — any civic regardless of its tech prerequisite — has **no data field anywhere**; it is SDK-implemented. That was first documented here as unrecoverable, which was wrong: the English prose is in `Assets/XML/Text/CIV4GameText_Strategy.xml`, keyed from the building's `<Strategy>` tag, and says it outright. The two sources are complementary rather than redundant — on the Pyramids the fields carry +6 culture and team-sharing that the prose omits, while the prose carries the civics unlock that no field has, and on the Library the prose names it as prerequisite for Universities, the Great Library and two national wonders. It is kept in a separate block and labelled as the game's own summary because it is **advice copy, not a spec**.

Only `[COLOR_*]` markup is stripped. The same square-bracket syntax carries **keyboard key names** in hotkey help — `[CTRL]`, `[F12]`, `[ESC]` — so a blanket bracket strip would mangle real content; measured 1220 colour tags against ~25 key names. English is taken from the bare `<English>` element, since the same block holds French, German, Italian and Spanish siblings and `<Description>` entries elsewhere nest theirs as `<English><Text>`.

**`EFFECTS MAY BE INCOMPLETE` still prints on every building.** Strategy text narrows the gap but does not close it — a complete-looking `EFFECTS` list invites exactly the wrong conclusion, the same authoritative-with-a-hole failure that made the units-only `UNLOCKS` block actively harmful. The block adapts: it explains the pairing where strategy text exists and warns harder where it does not.

**Free experience is nested, like the build prereqs.** `<DomainFreeExperiences>` holds Barracks' +3 XP; a flat field scan misses it entirely, which is how the trial ended up hand-deriving it.

**Build turns are per city, because early production is wildly uneven.** The same 50-hammer building is ~5 turns in Lisbon and ~25 in Oporto at t40 — a gap that decides the answer, and the state file already carries `productionPerTurn` per city. Same extrapolation caveat as research turns, with the added wrinkle that `productionPerTurn` carries one-off overflow the turn after a build completes.

**"What can I build right now" was refused, and that refusal is now reversed — by `city`, below.** The original objection was that the answer is **per city**, not per empire: `bWater` gates on coastal, `bRiver` on river, and prereq buildings are per city, so a single empire-wide list would be wrong for at least one city most of the time. Every one of those three objections names a fact that schema increment ⑤ then exported per city. The refusal stated its own unblocking condition and ⑤ met it.

**`city NAME` — what the empire-wide refusal got wrong.** Two errors, recorded because the second is the one that matters.

The **scale objection was measured wrong.** The case against listing was "the list gets long, then it needs a filter, and a filter is the query language" — backed by a probe reporting 123 tech-open units at t43. That probe read `unit["tech"]`; the parsed struct's field is `prereq_tech`, so the filter passed every unit in the file and the number was the file's size, not an answer. The real figure at t43 is **34**, then **30** after removing other civs' uniques (`CIV4CivilizationInfos.xml` settles this definitively — Portugal's sole override is `UNIT_PORTUGAL_CARRACK`), then **18** after dropping `iCost <= 0`, which is animals and great people rather than anything trainable. Of those 18, seven are Executives and seven are missionaries, both gated on things the player has no route to at t43. The genuinely live list is about four lines. A list that short never needs a filter, so the slope the refusal was defending against is not there.

The **substantive error was conflating discovery with comparison.** Repeated one-at-a-time lookups serve comparison — you know the candidates and want them priced side by side. They cannot serve discovery, because `rules.py unit UNIT_X` requires already knowing X exists. That gap was recorded in this file before the refusal was written: a trial made five calls guessing type names, found four unavailable, and said it was **relying on memory to know which units to even ask about**. That is a rule-5 violation with no fallback — there is nothing to grep for when you do not know the name — and it is the one failure mode the whole tool exists to prevent.

**What keeps it from being a query language is that the list is derived, not selected.** There is exactly one correct answer to "what can Lisbon build now": a function of tech, connected resources, `coastal`, `buildings` and the wonder state, with no parameters. That is why it cannot grow a `--filter` — there is nothing to filter *toward*. The thing still refused is `--sort by-value` or `--top 5`, which need a preference, and a preference is a ranking. Two rules make the line testable, both enforced:

- **Fixed order, never a useful one.** Alphabetical within a block, never cost, never best-first — the same discipline as the tech route block, whose no-ranking-vocabulary assertion this reuses.
- **Blocked items stay in the list with the blocker named.** This is what makes it presentation rather than a chooser. A buildable-only list is a *filtered* list and reads as a shortlist; `UNIT_CHARIOT ... BLOCKED - BONUS_HORSE visible at (79,37), no road` is the same fact plus the thing the player can act on. It is also the only version that answers "when do I switch production", which is a question about what is *about* to become available.

**`city` is the one view that must not use `effective_known`, and using it was the worst bug in this increment.** That set folds in the tech currently being researched — correct when costing a route, since you will have it before anything downstream matters, and wrong when the question is what the city can start building *this turn*. At t43 Masonry sits at 4/124 with seven turns left, and folding it in reported the **Pyramids, the Great Wall and Walls as available now**. Nothing in the output contradicted it: the rows looked exactly like the genuinely-available ones, and the only way to catch it was to read the tech list separately — which is the failure mode the whole tool exists to remove. `known` is now strictly `player.knownTechs`; `horizon_known` keeps the softer set, because a tech already being paid for is not "one tech away" on top of what is in the bank. A tech-gate sweep over all 44 turns × both cities asserts zero rows are ever marked available while their prerequisite is unknown. **`building` and `tech` were never affected** — they print `[RESEARCHING - 7 turns left]` and always did.

A blocker on the in-progress tech now says so: `needs TECH_MASONRY - RESEARCHING NOW, ~7 turns left`. "Needs Masonry" and "needs Masonry, arriving in seven turns" are different decisions — one is a plan, the other is a wait — and the second is exactly the case the blocked-rows-stay-listed rule exists to surface.

**Settlers and workers are built from food as well as hammers, and both halves of that were wrong at first.** `bFood` units convert the city's entire food surplus into production, so the city stops growing and the build lands much sooner. Ignoring it roughly doubled the quoted time on the two builds that dominate the early game. The export already carries it, and the baseline shows it cleanly on consecutive Lisbon turns: t42 `UNIT_WARRIOR` food 6 / prod 7, t43 `UNIT_SETTLER` food **0** / prod **13**. So `productionPerTurn` already contains the food while such a build is queued and `foodPerTurn` reads 0 — which means the correction is conditional, or it double-counts. (Increment ⑥ has since exported the split outright; the paragraphs below are the inference it replaced, kept because the fallback still runs them on every committed sample.)

The first fix handled that direction and introduced the mirror-image error: with a food build running, *ordinary* rows inherit food they would not get, and a Warrior read 13 hpt when its true rate is 7. The split was **not recoverable from one file** — Lisbon's hammers move 8 → 2 across t37 → t38 as worked tiles change — so it was flagged rather than silently used, once in the section header instead of on thirty rows. Food-fed rows carry `(+food, growth stops)`, because that trade belongs to the reader.

**Schema increment ⑥ closed that hole, and the flag is the thing that measures it.** The mod now exports `cities[].productionFromHammers` and `cities[].productionFromFood`, so an ordinary build is priced at the hammer half directly — no inference from what happens to be queued, and no "optimistic" caveat, because the case it existed for is exactly the one the split resolves. On t43 Lisbon the Warrior goes from `~2 turns` *(flagged)* to `~3 turns` *(plain)*, and the three-line section header disappears. `food_build_rate()` keeps the inference as a fallback and reaches for the exported fields when they are present.

This is the second time a value was reused across a semantic boundary here and the fix was to **export the distinction rather than reconstruct it** — the same shape as `coastal`, which the harness also could not derive correctly (see below). The tell was identical: a caveat printed in the output describing a limit of the tool rather than of the game.

**The whole baseline run now carries the split, but only `turn_0040` and `turn_0043` are genuine.** Those two saves were reopened and re-exported once the mod change landed; the other 41 city-bearing turns are **backfilled** by derivation — `food = max(0, Σ workedTiles food − 2 × pop)` for a `bFood` build, `hammers = productionPerTurn − food`. The full reasoning, validation and limits are in `samples/README.md`'s second provenance caveat; the short version is that recomputing the two genuine turns reproduces all four city rows exactly, and an independent trait-multiplier model agrees on 48 of 51 rows across the run.

**That trade costs the fallback branch its sample coverage, deliberately.** No turn in the run now lacks the fields, so the pre-⑥ path in `food_build_rate()` is exercised only by the synthetic unit tests. The sum assertion in the sample sweep is likewise vacuous on derived turns and meaningful only on the two genuine ones — which is why `test_the_backfill_derivation_reproduces_the_genuine_turns` exists: it recomputes the split from `workedTiles` and compares against the real export, so the formula that generated the other 41 turns stays pinned to ground truth rather than to itself.

The re-export is also the strongest evidence the change is inert: **the two files differ from their committed predecessors by exactly the four added lines, with not one existing value moved** — same tile count, same units, same contacts, byte-identical everywhere outside `cities`. A re-export of the same save reproduces the original, which is what makes the extra `getCurrentProductionDifference` call demonstrably free of side effects.

**t43 Lisbon confirmed the reconstruction exactly**: `productionFromHammers 7 + productionFromFood 6 = 13`, matching the figure inferred from the t42/t43 pair before any capture existed. **t43 Oporto is the more valuable row**, being a case the old inference got wrong in a way nothing flagged: a food build with a *small* surplus (`6 + 1`). The inference keyed on `producing.startswith("UNIT_") and surplus == 0`, so it read Oporto's 7 hpt total as an ordinary build's rate and priced a Warrior at ~2 turns against the true ~3. Both cities lost the "optimistic" header, since there is nothing left to caveat.

**`UNIT_SETTLER` has `iCost 0` in the BTS tree and 100 in vanilla, and the literal reading deleted it from the tool.** The `iCost > 0` filter that keeps animals and great-person builds out of the list took the 0 at face value, so the single most important early-game build was absent from every city. The engine settles it: `cities[].productionNeeded` reads 100 on all thirteen turns Lisbon built one. The fallback is deliberately narrow — **zero only**, never "prefer vanilla" — because BTS genuinely re-prices units (a Chariot is 25 in vanilla and 30 in BTS), and measured across the file exactly one unit is affected. A cost of 0 in *both* trees still means "a city never trains this", which is what the filter is for. This is the one place the BTS-first rule needed an exception, and it is an inheritance rule rather than a resolution change.

**The coastal contradiction was a defect, not a missing feature.** `BUILDING_LIGHTHOUSE` at t43 printed `city must be coastal` and, above it, `~5 turns in Lisbon` — Lisbon being `coastal: false`, where it cannot be built at any speed. The two lines contradicted each other and the tool could not tell, because `_city_build_turns` iterated every city and knew nothing about gates. It now takes the building and skips cities the gate excludes, saying so rather than silently shortening the list — an unexplained missing city reads as a data problem. Fixed without a flag, since a wrong number does not become right by being opt-out. **`coastal` is not derivable** from `map.tiles`: the engine's test is adjacency to a water body of a minimum size, so a harness deriving it from "is a neighbour water" would call a city on a pond coastal. This is the clearest case in ⑤ of a field that unlocked something rather than saving a grep.

**⑤'s resource half unlocked nothing, and that is worth recording too.** The obvious reading of increment ⑤ is that it enables the resource-prerequisite answer. It does not: `_resource_status` already consumed `player.bonuses.counts`, in the same commit that added it. Checked against the sharpest case in the sample rather than assumed — the Horse at (79,37), visible from t30, pastured t40, road completing t43 — `rules.py unit UNIT_CHARIOT` reports `2 visible tiles, but NOT connected / (79,37): no road` at t40 and `CONNECTED - 1 in your trade network` at t43. Correct on both sides of the transition, naming the specific missing link. What ⑤ actually unlocked is narrower and entirely per-city: `coastal`, `buildings` (prereq buildings are per-city state held nowhere else), and `wonders`.

**`wonders` was exported and then read by nothing.** `built` turns the world-wonder caveat from "a race you cannot check" into "already gone, stop" — the tool printed the honest-when-written line *"the export cannot see rival production"* while a field answering half of it sat unread. `national` does the same for one-per-player wonders, which otherwise quote a build time for something already standing. **The sample cannot validate this**: `wonders.built` is `[]` in all 44 files, so that branch is tested synthetically and this note is where that gap is written down. `national` is exercised, at `[BUILDINGCLASS_PALACE]` throughout.

**Only `turn_0040` and `turn_0043` are genuine for these five fields.** Turns 0–39, 41 and 42 have them backfilled (see `samples/baseline-early-game`'s provenance caveat in `samples/README.md`), so they are used for does-it-crash coverage and never as expected values.

**All three bugs above were the same mistake, and that pattern is the finding worth keeping.** Each reused a value whose semantics were right for its original caller and wrong for the new one: `effective_known` (costing a route vs. building this turn), `iCost > 0` (an untrainable animal vs. a cost BTS blanked), and `productionPerTurn` (a food-fed build vs. an ordinary one). None was a typo, each looked correct in isolation, and **none was caught by review — all three needed real captured turns**. The generalisation for anything added here later: a helper that already exists is the most dangerous thing to reach for, because it carries an assumption from its first use that nothing in the new call site restates. The check that actually worked was cheap — run the tool across every turn of the run and assert an invariant (no row available while its prerequisite is unknown), which is now a test rather than something remembered.

**The third of those was the only one that could not be fixed in the harness at all, and increment ⑥ finished it.** `productionPerTurn` was not merely being misused — it genuinely did not contain the information an ordinary build's rate needed, so the best the harness could do was flag its own answer as optimistic. That is the signature worth recognising next time: when the honest fix is a caveat rather than a correction, the missing distinction is usually upstream, in what gets exported, and a flag is a placeholder for a schema change rather than a resolution of one.

**How this was tested.** Six agent trials against the baseline run, each a fresh agent given only `AGENT_GUIDE.md` and the sample, each asked a real question and asked to report where a tool would have helped. Questions were chosen to be able to *fail visibly* rather than to demo the tool: the canonical Archer sighting, an Axeman feasibility question whose real answer is a resource the player cannot see, a barbarian-exposure question that needs the handicap, an explicit "what should I research" aimed straight at the decide-line, an open-ended threat question, and a Barracks question the tool deliberately does not cover.

**All six passed on the dimension the tool exists for** — no agent stated a tool-covered rule from memory, and two explicitly corrected the Archer→Bronze Working error in their own answers. Findings, and what each changed:

- **The route-cost block survives on trial evidence.** The "what should I research" trial priced Archery at 155 against Bronze Working at 187 and chose the **more expensive** one, on reveal-and-chopping grounds the tool does not rank. That was the case the block was most likely to fail, so it stays.
- **`handicap` was used unprompted in five of six**, and one called it the sharpest fact in its answer — `iFreeWinsVsBarbs 0` on Emperor with two empty cities. It also said it would have skipped it without the guide naming the subcommand, which is direct evidence for the guide's naming convention.
- **The `TechReveal` gap was the most consequential defect found.** Without it the tool reads as "12 turns to Axemen" when the honest answer is "12 turns to find out *whether* Axemen exist for you". The trial recovered it by grepping.
- **The backwards totals were caught in use, not in review.** A trial read `Prerequisites still needed: 62` as the cost of Archery when the answer was 155.

**A second round of four trials ran against the finished tool** (extended sample, t0–t43), chosen so each could fail visibly rather than demo the tool: the Axemen resource question, the Barracks question that previously had no subcommand, a three-way tech comparison aimed at the decide-line, and an open-ended "strongest play". All four passed, and across both rounds **no agent has stated a tool-covered rule from memory** — ten of ten.

What that round settled:

- **The guide cuts hold.** Six caveats were moved out of `AGENT_GUIDE.md` on the argument that the tool prints them at point of use. The Axemen trial recovered the copper-reveal caveat from output alone and phrased it better than the guide had: *"seeing zero now is not evidence you have none, and it is equally not evidence you have some."* That second clause is now in the tool.
- **The route/turn figures still are not read as instructions.** The tech-comparison trial recommended the *more expensive* tech and then argued against its own pick unprompted. That was the case the decide-line was most likely to fail, so the block stays.
- **The richer `UNLOCKS` drew no verbosity complaint**, and two trials used its new categories — Slavery, chopping, quarry, resources-usable — directly, all things earlier trials had filled in from memory.
- **`building` closed the gap it was built for.** The previous round's hand-grep is gone, and the "a rival may already be building this, you cannot check" caveat was credited with turning a maybe into a clear no.

**`improvement` is the only subcommand whose arithmetic is validated against the engine rather than against the XML.** Every other view reports values it read; this one *computes* a number the game also computes, which makes it the one place a plausible-looking mistake produces a confident wrong answer with nothing to catch it. So the view's own code path is checked against `map.tiles[].yields` across every turn of the baseline sample: **7,901 tiles, zero disagreements**, committed as `test_tile_yields_match_the_engine_on_every_sample_tile`.

That sweep is the most valuable test in the file, and it is deliberately routed through `nature_terms`/`improvement_yield` — the path the *view* takes — rather than through `nature_yield`. An earlier version swept only the latter, which is exactly how the peak bug survived: the two were separate accumulators, the fix landed in the swept one, and the view went on printing `2 food` for a plot the engine reports as `[0,0,0]`. Sweeping the path the output actually takes is what makes that class of divergence visible.

**It validates only what the tile is, never what it would become**, and that bound is structural rather than a coverage hole: the engine computes yields for tiles as they exist, so the `IF YOU BUILD` column is compared against nothing. The flood-plains bug lived there — a surviving feature's yield dropped from every projection while all 7,901 tiles still agreed — and no sample tile has a real improvement standing on a feature anyway (the only two are goody huts, excluded), so that interaction is unexercised on the validated side too. Counterfactual coverage is therefore hand-written per interaction. **The one cheap way to narrow it is a capture**, queued under `varied-setup-samples`: an improvement built on a feature-bearing tile becomes an ordinary swept tile the turn after the worker finishes, so ten turns with a worker buys engine validation that no amount of test-writing can.

It found three real bugs that all the hand-written tests had passed:

- **Peaks.** `calculateNatureYield` returns 0 for an impassable plot before reading terrain at all. Omitting that clause was worth 76 wrong tiles, every one of them plausible (grassland peak reading 2 food).
- **The city-centre floor.** `iMinCity` in `CIV4YieldInfos.xml` — 2/1/1 — is why a city on plains shows `[2,1,1]` and not `[1,1,0]`. Found by noticing that 69 mismatches were all city tiles; it is not discoverable from the improvement file at all.
- **Nested containers.** Three separate fields were read from the wrong depth, because these files reuse the *same tag name* inside child structs. An `ImprovementInfo`'s own `<YieldChanges>` and the `<YieldChanges>` inside each of its `<BonusTypeStruct>`s are indistinguishable to a non-anchored regex, so the Farm's flat yield came back as Corn's +2 and the tile totalled 6 food. Likewise `<PrereqTech>` returned `TECH_BIOLOGY` — the Farm's *late* yield tech — as though it were the unlock. Hence `_without_nested`, and the note that a wrong inner tag name returns `None` rather than raising, so the symptom is always a silently missing term.

**The tech that unlocks an improvement is not on the improvement.** Every stock `ImprovementInfo` has an empty `<PrereqTech>`; Agriculture, Mining and Pottery live on `BUILD_FARM`, `BUILD_MINE` and `BUILD_COTTAGE`. Reading the improvement's own field yields `None`, which renders as "no tech needed" and is wrong for nearly every improvement in the game.

**`bBonusMakesValid` is an early `return true`, not one condition among many.** In `canHaveImprovement` it sits *above* the flatlands, irrigation, feature and nature-yield gates, so a resource that validates an improvement bypasses all of them — which is why a Farm is legal on dry Corn and on hill Corn. The port keeps the source's clause order for exactly this reason; reordering it to read more naturally would silently produce the wrong answer on resource tiles, which are the tiles anyone actually asks about.

**A feature never makes a tile illegal**, and an early version of this tool reported otherwise. `canHaveImprovement` consults the feature only through `FeatureMakesValid` and `bRequiresFeature`, both of which can *add* validity; the forest on a hill costs a **tech**, not legality, because clearing it is part of performing the build. That distinction is the whole content of the trial's second wrong answer, so it is reported as a requirement beside a legal verdict rather than as a refusal.

**Provenance of the ported source is weaker here than elsewhere in the repo, and is stated rather than glossed.** The install ships only a compiled DLL, so the C++ came from two bundled mod SDK copies rather than from Firaxis. The full argument for trusting it — and the one function where the two copies diverge — is in `REFERENCES.md`; don't repeat the claim without reading it.

**Financial is the only trait affecting tile yields, and it is read rather than hardcoded.** `<ExtraYieldThresholds>` is a positional triplet whose commerce slot holds 2, meaning "+1 on a tile already making 2+". It is applied last, after the city floor, matching `calculateYield`'s own order. The join to get there is awkward and worth knowing: **the state file exports no traits at all**, only `player.leader`, so the leader → trait lookup goes through `CIV4LeaderHeadInfos.xml`. For a rival's tile the leader comes from `contacts`, and an *unmet* owner returns "traits unknown" rather than an empty tuple — computing their tile as though they were traitless would be a guess dressed as an answer. The baseline sample's João is Imperialist/Expansive, so none of this is exercised by the sample and it is covered synthetically.

**`canHaveImprovement` is not the whole gate, and the two clauses it misses both produced confident wrong answers.** It answers "could this tile hold this"; `CvPlot::canBuild` wraps it with checks that have nothing to do with terrain. Two bite in ordinary play, and the first output shipped without either: a tile **already carrying** the improvement (or one that upgrades into it — a Cottage where a Hamlet stands), and a tile **inside another team's borders**, where nothing is buildable bar the few `bOutsideBorders` improvements. Offering a Farm on a tile that already has one is merely noise; offering improvements on Alexander's land is advice to do something the game refuses, with nothing in the output to hint at doubt. Both now resolve through `build_blocker`, and the empty case names *which* of the three reasons applies — "nothing can be built here" reads as a property of the ground, which on foreign soil is the wrong conclusion entirely.

**`NOW` reports the tile's current yield including whatever is already built on it.** It first read the bare-terrain figure, which understates the status quo and makes every alternative look better than it is — and since each row's change is measured against `NOW`, that error propagated into every option. On the sample's farmed wheat tile it turned "swap the Farm for a Cottage, **−3 food** for +1 commerce" into a free-looking +1.

**Output length was cut roughly in half against real captures, after reading them rather than from the outset.** What went: the route line and the trait list (neither changes an improvement choice, and a non-Financial leader's traits are pure noise); the repetition of unchanged yield columns in every row, which was the single largest source of bulk since the unchanged ones are already on the `NOW` line; and a four-line-per-row layout collapsed to a header carrying total and delta together. A typical tile went from ~45 lines to under 25. The OMITS block is now the largest fixed cost, which is the right thing to be paying for.

**Resource connection is flagged because the yield columns actively mislead on resource tiles.** Player-observed: *"on tiles with a bonus resource it very rarely makes sense to build any other improvement."* The tool was printing a Cottage's +1 commerce beside a Pasture's +2 hammers with nothing to say that only one of them connects the horses — and the connection is worth more than either yield, since a strategic resource gates whole unit lines. So each row now carries `<- CONNECTS X`, `leaves X unconnected`, or `LOSES X` where it would replace a connector already standing.

**It stays a lookup rather than a judgement**, which is what makes it admissible under the no-ranking line. `bBonusTrade` is the engine's own gate (`CvPlot::updatePlotGroupBonus` adds a bonus to the plot group only if the tile is a city or carries an improvement whose `isImprovementBonusTrade` names it), and it resolves to **exactly one improvement per bonus** across all 32 in the stock files — the sole pair being Oil's WELL/OFFSHORE_PLATFORM, which the tile's own land/sea status separates. `bBonusMakesValid` and `bBonusTrade` are set identically on every struct in both trees (checked), so the connector is always also legal. The connector is sorted first: **ordering, not ranking** — it is not a claim it yields most, since a Mine on Gems is −1 hammer.

**The `TechCityTrade` gate is surfaced separately because it is the player's stated exception.** A resource needs its own tech before any city can work it, distinct from the build's prerequisite and checked *first* by the engine — Wine needs Monarchy, Spices and Dye need Calendar. That is precisely when a non-connecting improvement is the right call, so the view prints the gate rather than leaving the connector looking unconditionally correct. The field was already parsed (`city_trade`) and simply unused here.

**The improvement list is an exclusion set, not an inclusion one.** A mod's new improvement shows up by default; the excluded ones are named explicitly. A tool that silently omits something buildable is the exact failure mode this item exists to fix, and one extra row is far cheaper than none.

**Those exclusions are two lists, not one, and fusing them is a latent bug.** `NOT_REAL_IMPROVEMENTS` (the `*_WORKED` markers, city ruins, goody huts) is a *modelling* fact — a tile carrying one is bare ground, and running a hut through the yield accumulator "clears" the forest under it. `OUT_OF_SCOPE_IMPROVEMENTS` (Lumbermill, Windmill, Watermill, Fort, Well, Offshore Platform, Forest Preserve) is a *scope* choice about what the view offers. They were one constant serving both purposes, which happened to work only because the sets are disjoint today: widening the turn window means deleting from the second list, and under the fused version that would silently have changed how an existing improvement standing on a tile was valued — reverting `NOW` to the bare-terrain baseline with a wrong-but-plausible number and no failing test. A Windmill this view declines to *offer* still produces yields when one is already there.

**Startup cost was cut 38% (0.91s → 0.57s) by fixing a pre-existing quadratic in `iter_blocks`.** It counted newlines from byte 0 for every block to report a `file:line` citation — O(n²) in file size, measuring 159ms on the 1.1MB `CIV4BuildingInfos.xml` alone. Now a precomputed newline index plus `bisect`. This work made it worth finding (the improvement subcommand adds five XML files, including a 530KB leader file), but the fix benefits *every* subcommand, and byte-identical output on the pre-existing views was verified before and after.

**Findings recorded rather than built are now queued in [`ROADMAP.md`](../ROADMAP.md)**, with their trial counts — including the four that landed on the other tools rather than this one. They are all presentation rather than judgement, which is why they were recorded rather than refused; the things that *were* refused, and why, are under **The bar** above.

One is worth keeping here in full, being an argument about scope rather than a queue entry. **Per-city buildability and "how fast can I field X"** were both scoped by the trials to a **named city**, and that is what answered the objection which had killed the empire-wide chooser: `bWater`, `bRiver` and prereq buildings vary per city, but `rules.py city Lisbon` does not have to generalise. The refusal was reversed because the request arrived already carrying the constraint that made it buildable. The trial evidence behind it: one agent made five `rules.py unit` calls guessing type names to discover four were unavailable, and said it was *relying on memory to know which units to even ask about* — the failure the guide's rule 5 names.

</details>

### The bar

**A tool earns its place only where the agent is *unreliable* reading the raw JSON — not merely where automation is possible.** The agent reads JSON well; filtering units, comparing city yields and checking research all work unaided, so most of the export needs no tooling. The gaps are spatial reasoning, aggregation across many files, and consistent arithmetic over many rows. That is why this list is short, and it should stay short.

**Tools present; the AI decides.** Showing a candidate city site's worked radius with yield totals, resources and minimum-distance legality is *rendering*. Ranking candidate sites is *deciding* — the strategic judgement then lives in Python and the AI only reads out its conclusions, which defeats the premise. Site evaluation is where that line gets crossed by accident.

### What got built, and what the sketches got wrong

All three planned tools are done, plus `bearing.py` which the trials asked for. Each departed from its original sketch in ways worth keeping, all from measuring rather than predicting:

- **`render_map.py`** — five views, exercised across fourteen agent trials. The view set has held up: `settle` and its `--around` site report carry the city-placement decision, `military` gets opened whenever a settler has to walk, and `yields`/`worker` were worth splitting out of the original `empire` because "which tile should this citizen work" and "what should this worker build" want almost disjoint data.
- **`run_history.py`** — `timeline`, `intel` and `lost`. Run validation became a **constructor assert that exits non-zero** rather than something reported and worked around, once branch-divergence support was ruled out of scope; and every rival-unit departure is **classified against the next turn's fog**, without which a position-keyed diff is mostly noise. A third `check` view was designed and dropped when the assert absorbed it.
- **`rules.py`** — `unit`/`tech`/`building`/`promotion`/`city`/`handicap`/`goody`/`improvement`. **Handicap was added despite being a forward lookup**, on the roadmap's own reasoning rather than its wording: "the agent greps forward lookups fine" is falsified for these fields by two trials that changed conclusions on them. **The state file became mandatory** once the cost multipliers were measured — game speed × world size × handicap put a base XML cost 1.0–4.5× off, so an unpriced lookup is not a cheaper answer but a wrong one. And **depth turned out not to need a limit**: the tree is 92 techs wide and shallow, largest full closure 14. **`city` landed as its own subcommand** rather than the sketched `--city` flag: discovery is a different question from "tell me about this thing", and hanging it off `building`/`unit` would have meant naming a specific item in order to find out what the items are. The flag was then not needed at all — `building` already reports per-city build turns, so the same gate check simply filters that list and names who it excluded.

  **`promotion` took `TYPE` as a single positional, tried `nargs="*"` for several TYPEs at once, then reverted.** The multi-TYPE draft let one call total several promotions held together on a unit, but argparse's greedy matching for a variable-length positional cannot backtrack around a value-taking flag placed between it and the required `state` positional — a real limitation (reproducible with a two-line `ArgumentParser`), not a config mistake, and it broke ordering for every subcommand, not just `promotion`. **`--for-unit ID` replaced it**, reading `units[].promotions` from the state file itself rather than asking the agent to type each name — the only real use case for "several promotions at once" was seeing what one actual unit holds, which an id lookup answers directly and a hypothetical combination never came up. **`CAN TAKE NEXT`/`BLOCKED` (the `canAcquirePromotion`/`isPromotionValid` eligibility cascade) sits behind `--eligible`, off by default**: the common question is "what does this unit have", and `BLOCKED` alone lists every promotion in the file, which is real information but not something to print unread on every call.

The rules tool's premise got validated three times during its own construction: a hand-grep, a remembered combat modifier and a worked example each produced a confident wrong answer that the parsed XML caught (details in the design notes).

**What is still unbuilt — including the requests trials keep repeating — is in [`ROADMAP.md`](../ROADMAP.md), along with what this folder deliberately will not build.** The reasoning behind those refusals is above, under **The bar**.

### The agent instructions — written, in `AGENT_GUIDE.md`

Both requirements this section used to specify are there: it names each tool and when to reach for it, and asks the agent to **flag where a tool would have helped**.

That second one is validated rather than assumed — five trials produced those reports unprompted, and they were the most useful output of the exercise. Three independently asked for a defender-count join, two misread a consumed settler as a combat loss, and the unanimous failure was **compass direction**: every trial read coordinates correctly and then narrated north and south inverted, mirroring the strategic picture with nothing in the output able to catch it. Hence the guide's ordering. (The export has since inverted the y-axis outright — see `REFERENCES.md` "The y-axis inversion" — but the guide still leads with orientation.)

It contains no rationale by design; the reasons live here. The split itself — **usage and traps in the guide, reasons in the README** — is recorded as a design decision in the root `CLAUDE.md`.

**Rule 5 ("check the XML, never recall a rule from memory") is now a table keyed to output shape** — "about to say tech X reveals resource Y" → run `rules.py tech X` — rather than a prohibition. Same fix shape as the compass: noticing you're about to recall from memory is itself the failure mode, so a checkable trigger survives where a rule to introspect does not. A "confirm a gap before reporting it" line sits beside it. The anti-grep line was loosened too: "use `rules.py` rather than grepping" reads as *don't grep*, which suppresses the fallback for anything the tool doesn't cover — it now says grep BTS-then-vanilla and report having had to.

**The session brief's tool list and five-trap summary were cut, not reformatted.** Both duplicated `AGENT_GUIDE.md`; a duplicate is a second copy to drift, not a convenience. Deliberately not split into a third file — the existing guide/session-brief boundary already separates usage from reasons.

**The brief's working section is one numbered per-turn checklist, and the fact that it is *one* is the point.** A per-turn diff routine (`player.gold`, `knownTechs`, unit positions, city production) was added first and standing alone; it is now item 1 of that list. The failure being fixed is not missing instructions — the brief already asked for objectives restatements every 5–10 turns and got one at t0, updated to t10, then nothing through t36. **This is the compass lesson a fourth time: when a caveat does not stick, change the structure rather than adding words.** A checklist works because it is checkable at a fixed moment; a paragraph asking for diligence is not. Adding a checklist *beside* the diff line would have left two competing per-turn routines in one file — the same fragmentation that let the objectives instruction get ignored. All of it is unmeasured until the next trial.

**Bearings are an output convention, not a tool feature — no tool changed.** `bearings-by-default` was queued as a cross-tool build (bearing-from-nearest-city as the default rendering in `render_map`'s resource list, the `--around` header, the foreign-unit summaries), colliding with Lanes A, B and C at once. It read the evidence one layer too low: the player cannot see `(x,y)`, but **they never read tool output** — only the agent does, and the agent reads coordinates fine. That build would have widened every line in three modules and rewritten three test suites to decorate an interface with no human on the other end. The gap was in the agent's own prose, so the fix is a guide rule, a checklist item and a set of triggers in the session brief — no code. Anchoring on a *landmark* stays a judgement call — what is salient on screen is not computable — which is why it did not become a `nearest_city_note` call; `bearing.py` already covers the wrap-aware arithmetic that genuinely needs code. A `--landmark` mode was considered and dropped: it would have automated the case that already works, while the case that actually fails is a phrasing default with no computation in it at all.

**The brief now splits every answer at a `## My Recommendations` heading, and that heading is what makes the bearings rule enforceable.** The rule above had no fixed moment to fire at: "never give the player a coordinate" applies to a whole answer, so it is a property to maintain continuously rather than a step to take once. The split gives it one — reasoning and coordinates above, the player's turn order below — and the translation happens at a single crossing rather than everywhere at once. It also fixes a second problem the player raised: recommendations were interleaved with working-out, so the actionable half had to be extracted by reading.

**The coordinate rules are phrased as when→then triggers there, not as prohibitions**, at the player's request — a "don't" names the failure without supplying the replacement and fires as an after-the-fact check, while a trigger fires as the sentence is written. The player's own reason is that a prohibition makes the forbidden thing salient. The mechanism the evidence supports is narrower: the coordinate is already in working memory from tool output and reads like an answer, which is why the guide's own note says this is "the one that slips". Both point the same way, and it is the same fix shape as rule 5's table above. One short prohibition was deliberately kept beside the triggers — a coordinate below the line is a defect — because it is what makes the rule checkable when reviewing a trial transcript. **A fourth trigger, for coordinates smuggled back in parentheses, was written and then cut: no trial has ever done it.** It came from `AGENT_GUIDE.md`'s "not even in parentheses as a fallback", which is itself reasoned anticipation rather than an observed failure — the ten recorded trial failures are all compass direction. A guarded-against failure nobody has committed costs the same attention as a real one and teaches the reader that this file's rules are speculative; if a trial does it, add it back with the transcript. **`AGENT_GUIDE.md`'s "How to answer" still carries the older prohibition phrasing**, left alone deliberately to keep the blast radius to one file; converting it is unqueued and would want a trial's evidence first.

**The Findings checks became a table and now require the value quoted inline, because the silent version measurably did not hold.** The Qin Shi Huang trial re-committed the Warrior-movement error *with its checklist item in place and the block open* — it skimmed instead of reading. **That is the compass lesson a fifth time, and the first with measured evidence rather than reasoning behind it** — an instruction to check something is unverifiable by the agent writing it and by the player reading it, so it degrades to nothing with no signal. Quoting the value inline forces the eye onto it; "I checked" does not. **Scoped deliberately to the table's rows and to above the line** — the tempting generalisation ("quote a field for any claim one would settle") fires on nearly every sentence, which is unbounded and therefore uncheckable, and it would put field names back into the recommendations half two passes just cleaned out.

**Two rows were added from that trial, and one of them is not a lookup.** *Ownership* (proximity read as border) is an ordinary field check and also became guide trap 7, matching how the yields row splits between guide and brief. *Scope* is different in kind: the trial answered "what improves yields" for the worked tiles only, quoted every number correctly, and missed a Horse in `objectives.md` — nothing was misread, so no field or view could have caught it. It sits in the table anyway because the table is where claim-shaped disciplines live, and its row states the discipline directly ("say what you checked and what you didn't") rather than naming a field to quote. **A tool cannot detect a question it was not asked**, which is also why `ROADMAP.md` records it with no promotion path.

**The brief is now held to the same usage-not-reasons line as `AGENT_GUIDE.md`.** It had accumulated the justifications alongside the instructions — why a trigger fires where it does, why quoting beats checking, why the scope row is unlike the others — because each was written at the moment its rule was added, when the argument felt inseparable from the instruction. It is not: the agent needs the rule, and a rule that ships with its own defence invites re-deciding it every turn on a file read every turn. The arguments moved here, including the failure evidence: a clause naming the trial that skimmed and stated the wrong number was kept at first, on the grounds that a rule reads as arbitrary without the failure behind it, then cut too. **Evidence is persuasion, and persuasion is reasoning** — the agent needs the rule, not the case for it, and an anecdote about a previous trial invites weighing whether this one is the same. The guide's traps still carry theirs, which is a real inconsistency: those are read once, while the brief is read every turn, and that is the whole difference.

**A repeated recommendation was refiled from the agent's own diagnosis, and the refiling is the substance.** The agent recommended an unselectable tech twice and proposed a tech-specific checklist item, calling the repeat "a narrower version" of the scope finding. It is not: scope was answering a narrower question than asked, while this is carrying a conclusion across turns without revalidating it — **guide trap 1, applied to your own conclusions rather than to observations.** Trap 1's examples are all sightings ("a Roman Archer was at (69,31) on t26"), so the form that decays fastest is the one it never showed. Fixing it as a tech rule would have left the same shape to recur in a different costume — a settling site, a build order, a rival assessment all go stale the same silent way. So the general case went into trap 1, and the tech-specific gap (rule 5's table is keyed by claim shape and had no research row, reading as buildings and units) got one row each in the guide and the brief. **The agent's "check every time, even a tech recommended before" was deliberately not taken as written** — an always-on rule with no fixed firing moment is what already degraded once; anchoring it to *the moment of repeating* gives it one. Nothing here would have caught the first recommendation, which is stated in `ROADMAP.md` rather than papered over: a row makes the claim checkable, only running the tool makes it right.

**Those table rows encode `ROADMAP.md`'s `Findings` observations rather than tool usage**, which converts that section from a passive accumulator into something a trial actively tests. None is a known problem in any future run; the brief says so, because an agent told to watch for a mistake it is not making will find one.

**The out-of-band-fact protocol went to the agent, not to the player**, despite being a player-facing idea in origin. The agent is the only party present every turn, and a player-facing file is one nobody opens the session to read. The instruction is to name any fact arriving by voice — "it actually healed", "here's the 60 gold", "it took two promotions", "that number disagrees with the city screen" — as an export gap at the moment it arrives. **Its own limitation is stated in the brief rather than hidden:** this only catches the half where the player speaks first, because the wrong-but-plausible class is by construction invisible from inside a self-consistent view. That is the argument for it being load-bearing, not against it — every defect of that kind found so far, including increment ⑧'s wrong-and-test-passing `turnsLeft`, surfaced this way and no other.

**The tool half was deliberately not taken in the same sitting.** An `objectives.md last written: t10 (26 turns ago)` line in `run_history`'s header is the structural backstop for the one checklist item that still depends on the agent remembering. It is `run_history.py` — a different lane — and it carries a trap: `objectives.md` lives in the trial folder while the tool takes the run folder, and that run folder is a junction, so walking up from it resolves into the repo's own `state/` rather than the trial folder. A sibling-directory guess would report "never written" every run, looking exactly like real drift. Queued as `objectives-age-line`, which carries the measurement.

**The session brief now lives as `advisor/CLAUDE.md`, deployed by `advisor/new_game.ps1 -GameDir <name>` rather than pointed at directly** (reasoning for the junctions and why it builds outside the repo is in the script's own docstring). One consequence worth recording here rather than there: this is what let the split-mount caveat drop out of the trial instructions altogether — `config.local.json` now sits where `find_repo_root()`'s walk-up actually lands, since the generated folder is a real, contiguous tree rather than several separately connected ones.
